# 15 ガイド枠と表示のずれを直した記録

ライブのガイド読み取りで「ラン認識が悪い」「本体色をカラーコードとして
検知する」という症状を追い、原因を 2 つに分けて直した記録。

どちらも**値そのものは壊れていない**（`doDetect.sh` の 正解 32 / 誤答 0 は
一貫して不動）。壊れて見えていたのは、表示と、ガイド経路の解析条件だった。

## 1 症状

- 画面のバンドが本体色（ベージュ・白）で埋まり、`WHT 9` のような
  カラーコードとして描かれる
- ガイドに合わせているのに読み取れない・確信度が低い

## 2 原因 A: 表示だけが独立分類のままだった

### 2.1 何が起きていたか

拾い直しのしきい値を下げた（`RECOVER_DELTA_E` 9 → 3、`docs/13` §12）とき、
本体との CIE76 が 3 しかない区間、つまり**ほぼ本体色そのもの**がランとして
拾われるようになった。これが安全なのは「金属容疑の安全弁」とセットだから
だが、**安全弁が効くのは `jointDecode`（値の決定）だけ**だった。

画面に描くバンドは `toBands`（パレット最近傍の独立分類）で作られ、
`bodyLab` を一切見ない。オーバーレイはその結果をそのまま描いていた。

### 2.2 実測

43 枚で拾い直しのしきい値を振り、**表示に出る「本体色に近いラン」**を数える。

| `RECOVER_DELTA_E` | ラン合計 | 本体色に近いラン |
| ------ | ------ | ------ |
| 9（旧） | 167 | 9 |
| **3（現行）** | 180 | **25** |

16 枚で本体ベージュが末尾に「黄」バンドとして現れる
（例: `10-100ohm` が `brown, black, brown,` + **yellow**）。
値は安全弁が守るので誤答 0 のまま — 「値は合っているのに読み取りが
壊れて見える」という症状と一致する。

### 2.3 直し方

**画面と値を同じ解釈から描く。** `analyzeRoi` が `joint`（役割つきの解釈）を
返すようにし、オーバーレイは `usedRuns` / `droppedRuns` を受け取って、
採用されなかったランを破線・半透明・意味「除外」で描く。焼き込み画像
（`annotate/render.ts`）が以前からしていた描き分けを、ライブにも通しただけ。

あわせて `annotate/read.ts` が `jointReadResistor` を**呼び直すのをやめた**。
同じランで二度デコードしていたので、条件を 1 つ取り違えれば
「画面の解釈」と「値の解釈」が食い違う構造だった。

結果（43 枚、本体色に近いラン 25 本）:

| 描かれ方 | 本数 |
| ------ | ------ |
| 「除外」として描かれる | **23** |
| カラーコードとして残る | 2 |

残る 2 本はデコーダが金・銀として実際に採用したもので、正しい表示。

## 3 原因 B: ガイド枠をそのまま「検出した本体」として渡していた

### 3.1 何が起きていたか

ガイド経路（`debug/analysis/runAnalysis.ts` の `box` モード）は、ガイド枠を
検出済みの枠として `analyzeOptions` に渡していた。ガイドは「ここに合わせて
ください」という目印なので**必ず本体より大きい**。枠 = 本体の前提で組まれた
条件がまとめて外れる。

1. `bodyColumns` が背景の列まで本体と申告し、机や基板がバンドになる
2. `bodyRows` が本体の外に走査線を並べる
3. `rectify` は短軸を `targetHeight` に正規化するので、**枠が太いぶんだけ
   長軸の分解能が落ちる**。太さ 2 倍の枠ではバンド 1 本の幅が半分になる

### 3.2 実測: 効いているのは短軸

auto 検出で得た枠を膨らませ、43 枚で測る。

| 枠（長さ / 太さ） | 正解 | 誤答 | 保留 |
| ------ | ------ | ------ | ------ |
| 基準 x1.0 / x1.0 | 32 | 1 | 10 |
| 長軸のみ x1.4 / x1.0 | 28 | 2 | 13 |
| **短軸のみ x1.0 / x2.0** | **2** | **12** | 29 |
| 両方 x1.4 / x2.0 | 7 | 9 | 27 |

長軸の外しは穏やかだが、**短軸の外しは壊滅的**。3 の分解能低下が主因。

### 3.3 直し方

`core/shrink.ts` の `shrinkBoxToBody` を足し、ガイド枠を解析条件に渡す前に
本体へ絞り込む。

- 行の色（中央の列の中央値）を中央から外へたどって短軸を決める
- その本体行で列の色を測り、バンドを途切れとして跨ぎながら長軸を決める
- **明度は見ない**。円筒形ボディは縁へ向かって暗くなるので、明度を混ぜると
  陰影だけで縁と判定する（`color/anchor.ts` と同じ理由）
- **中心と角度は動かさない**。利用者がガイドに合わせた結果を信じる
- **小さくする方向にしか動かさない**。枠より大きい本体は `refine.ts` の領分

`refine.ts` は**伸ばす**専用で、細長さ 2.4 以上の枠には手を出さない。
ガイドの細長さは 3.5 なので素通りする。縮める側を別に置いたのはこのため。

### 3.4 実測: 絞り込みの効果と余白

| 枠 | 絞込なし | 両軸・余白 0 | 両軸・余白 0.08 | 両軸・余白 0.15 |
| ------ | ------ | ------ | ------ | ------ |
| 基準 x1.0 / x1.0 | 32 / 1 | 26 / 5 | 29 / 2 | 30 / 3 |
| 膨張 x1.4 / x2.0 | 7 / 9 | **29 / 1** | 27 / 4 | 28 / 4 |
| 膨張 x1.7 / x2.5 | 0 / 4 | 25 / 5 | **27 / 5** | 25 / 6 |

（正解 / 誤答。43 枚）

- 縁ちょうどで切ると円筒の肩と端のバンドを削るので、**少しだけ外を残す**。
  余白なしでは、すでに本体に合っている枠を絞るだけで 正解 32 → 26 に落ちた
- 余白 0.08 と 0.15 は正解の合計で並ぶが、誤答が 11 対 13。**0.08 を採る**

短軸だけを絞る案も測ったが、膨張が大きいほど負ける（x1.7 / x2.5 で
両軸 25〜27 に対し短軸のみ 16〜19）。枠が長いぶん背景の列が増えるため。

### 3.5 絞り込みは auto 経路には掛けない

すでに本体に沿っている枠を絞ると 正解 32 → 29〜30 と落ちる（3.4 の 1 行目）。
`readResistorImage`（auto・バッチ・較正）は従来どおり `refine.ts` だけを
通す。**絞り込みはガイド経路限定**。

## 4 表示の副産物: 枠を 2 つに分けた

赤い枠が「解析が本体と見なした範囲」になったので、利用者が合わせる目印は
白い破線の長方形（`drawGuideOutline`）に分けた。両者がずれていれば、
それ自体が「もっと枠に合わせて」という手がかりになる。同じ色で描くと
ずれに気づけない。

## 5 やらなかったこと

- **`toBands` に `bodyLab` を渡す**（本体近傍のランを分類段階で潰す）。
  表示を joint に揃えれば足りるうえ、分類と解釈の責務が混ざる
- **拾い直しのしきい値を戻す**。ラン数の回復は `docs/13` §12 で測って
  採った施策で、値には効いている。表示の問題を値の側で直す筋ではない
