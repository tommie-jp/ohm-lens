# OhmLens — 色空間と色差指標の検討

2026-07-28 作成。「カラーコードの識別にどの色空間・どの色差指標を使うか」を
検討した記録。[04-色判定方式の検討.md](04-色判定方式の検討.md) が
**分類方式**（ボトムアップ分類 vs トップダウン候補照合）の検討なのに対し、
本書は**色をどの空間で測るか**に絞る。

> **結論: 色差指標は ΔE2000 のまま据え置く。色空間の差し替えは優先度が低い（§7）。**
>
> 当初は HyAB への差し替えが有力と見立てたが、**実測で否定された**。
> 基準色テーブルどうしの余裕（§5.2）と実写での当てはまり（§5.3）は一致しない。
> [07-色帯読み取りの改善.md](07-色帯読み取りの改善.md) の流儀に合わせ、
> 効かなかったことも根拠付きで残す。

## 1. 現状の構成と、それが壊れている箇所

色差指標は用途で使い分けている。これは意図的な設計で、`core/color/colorSpace.ts`
のコメントに理由がある。

| 用途 | 指標 | 実装 |
| ------ | ------ | ------ |
| 区間の切り分け（同じ色の区間か、別の色か） | CIE76（Lab のユークリッド距離） | `core/bands/runs.ts` の `splitRuns`、`core/bands/segment.ts` の `mergeAdjacent` |
| 基準色への分類（どの基準色に最も近いか） | ΔE2000 | `core/bands/classify.ts` の `rankBandColors`、`core/bands/align.ts` の `matchCost` |

切り分けに CIE76 を使うのは、**ΔE2000 が高彩度域の差を圧縮する**ため。
「本体ベージュと金バンド」のように彩度だけが違う組を近いと判定してしまい、
バンドが本体に吸収される。分類には知覚的に均一な ΔE2000 を使う。

**本番の分類主経路は `classifyBandColor` ではなく `rankBandColors`**
（`core/value/jointDecode.ts` の `candidatesFor` から呼ばれる）。
`segmentBands` / `Band.confidence` は表示用で、値の確定には使われない。
`isBodyColor` は現在どこからも呼ばれていない。

### 現状の実測値域が壊れている（原因は白飛びではない）

`diagnose-report.txt`（08-47ohm.jpg）では ROI 端の列が **L\*127.2** になっている。
L\* の定義域は 0..100 なので、これは値域外。

当初「肩の鏡面反射による白飛び」を疑ったが、**実測で否定された**。
39 枚それぞれについて、本番の本体窓
（`roiMapping.ts` の `bodyColumns(box, ROI_OPTIONS, 0)`）内の各列で
中央 50% 行のチャンネル別中央値を取り、全チャンネル 250 以上の列を数えた結果:

| 測定項目 | 結果 |
| ------ | ------ |
| 飽和列が 0 の画像 | **38 / 39**（唯一 24-6.8kohm に 1 列） |
| `lightnessScale` が 1 を超える画像 | **39 / 39**（1.10〜3.75、中央値 1.33） |

**つまり L\*>100 は白飛びではなく、`core/color/whiteBalance.ts` の
`adaptToAnchor` による L\* の乗算だけが作っている。**
08-47ohm では本体基準 beige L\*75.4 ÷ 観測アンカー L\*58.6 = 1.28 倍。
青ボディの 23 は 2.98 倍、39 は 3.75 倍に達する。

`core/bands/profile.ts` に飽和ガードを入れても本番では 1 列しか変わらないので、
**飽和対策は不要**。

なお `L*` を 100 でクランプする対処は実測で**悪化**する（正解 28 は維持だが
誤答が 1 → 2 に増える）。理論的に正しい「線形輝度空間での補正」も 28 → 25 に落ちる。
理由は `sample/palette.json` が**この乗算変換の下で学習された中央値**だからで、
変換と palette は密結合している。**片方だけを差し替える A/B は意味を持たない。**

### 金が「ほぼ白」として学習される件の真因

`calibration.txt` では **金が「L\*125 a\*-7 b\*10」＝ sRGB[255,255,255]
として 17 件学習**され、`paletteOverrides` の誤学習ガード
（`core/learning.ts` の `MAX_REFERENCE_DRIFT`）で棄却されている。
白も L\*120、銀は 0 件。**`sample/palette.json` は 8 色しか持たず、
金・銀・白・灰は既定値（見た目からの推定）のまま運用されている。**

この L\*125 の正体は**白い机や紙**で、飽和画素ではない（生 L\*≈97 × スケール 1.28）。
較正パスだけがこれを拾う理由は 2 つ重なっている。

- `tests/fixtures/calibrate.test.ts` が `BODY_MARGIN = 0.18`（本番は
  `core/settings.ts` で 0）と `keepEdgeRuns: true` を使うため、
  **本番窓の外にある白背景ランが候補に残る**
- `core/bands/align.ts` の DP が**バンド側を 1 本もスキップできない**設計
  （`runs.length < bands.length` で null、終端で全バンド消費を要求）。
  金が本体に吸収されてランが存在しなくても、必ずどれかのランに金を割り当てる
  → 余った白背景ランが選ばれる

したがって直すべきは飽和でも L クランプでもなく、**較正窓を本番窓に揃えることと、
`align.ts` にバンド側のスキップを許すこと**。

> **注意**: L\* を 100 にクランプすると、金の学習値は L100 a\*-7 b\*10 となり
> 既定値からの CIE76 ずれが **60.07**。`MAX_REFERENCE_DRIFT = 60` の真上に来る。
> b\* の中央値が 1 動くだけで閾値を下回り、「金＝ほぼ白」が
> `sample/palette.json` に入ってしまう。現状ずれ 76 で棄却されているのは
> **偶然の安全弁**であり、クランプはこれを外す方向に働く。

## 2. カラーコード 12 色の幾何

基準色テーブル（`core/color/colors.ts` の `BAND_SRGB`）を CIELCh と OKLCh で
見たもの。本体ベージュも比較のため併記する。

| 色 | L\* | C\* | h | OK L | OK C | OK h |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 黒 | 11.3 | 0.0 | — | 23.5 | 0.0 | — |
| 茶 | 27.4 | 38.5 | 58.7 | 38.1 | 8.8 | 52.7 |
| 赤 | 43.2 | 77.6 | 35.7 | 53.5 | 20.3 | 27.6 |
| 橙 | 65.4 | 77.6 | 62.3 | 71.5 | 16.9 | 56.4 |
| 黄 | 84.0 | 75.9 | 95.3 | 85.9 | 16.6 | 99.7 |
| 緑 | 51.1 | 58.4 | 144.5 | 56.3 | 15.1 | 147.7 |
| 青 | 34.2 | 68.0 | 295.5 | 44.4 | 17.8 | 266.9 |
| 紫 | 39.4 | 56.3 | 313.5 | 49.4 | 14.5 | 307.6 |
| 灰 | 54.4 | 0.0 | — | 60.7 | 0.0 | — |
| 白 | 96.5 | 0.0 | — | 97.0 | 0.0 | — |
| 金 | 67.8 | 59.6 | 86.2 | 72.4 | 13.1 | 87.9 |
| 銀 | 77.7 | 0.0 | — | 80.8 | 0.0 | — |
| 本体ベージュ | 75.0 | 24.9 | 78.4 | 78.6 | 6.4 | 74.6 |

読み取れる構造:

- **無彩色 4 色（黒・灰・銀・白）は C\*≈0 で、色相が存在しない。**
  L\* が 11 / 54 / 78 / 97 とほぼ等間隔に並ぶので、この 4 色は L\* だけで決まる。
  逆に言えば、等方的なユークリッド距離だとノイズだらけの色相成分を距離に混ぜてしまう
- **茶と橙の色相差は 3.6° しかない**が、L\* が 27.4 対 65.4 と大きく離れている。
  この組は色相ではなく明度で分離する色
- **金は本体ベージュと色相がほぼ同じ（86.2° 対 78.4°）で、彩度だけが 2.4 倍違う。**
  金/黄も色相差 9.1° と小さい
- 金・銀は本来「色」ではなく**金属光沢**なので、色空間の選択では原理的な上限がある

## 3. 実測での金／本体の関係

`diagnose-report.txt` の 08-47ohm.jpg の列を LCh に置き直したもの。

| | L\* | C\* | h |
| ---- | ---- | ---- | ---- |
| 本体ベージュ（実測） | 73–76 | 25–27 | 80° |
| 金バンド（実測） | 73–76 | 51–57 | 87° |

**明度が同じ、色相もほぼ同じ、彩度だけが 2.1 倍違う。**
基準値（金 C\*59.6 / ベージュ C\*24.9）ともよく一致しており、
**この組に関してはパレットは大きく外れていない。外しているのは距離の測り方**。

## 4. 検討した色空間

| 色空間 | 評価 | 理由 |
| ------ | ------ | ------ |
| CIELAB（現行） | 継続 | 明度と色味が分離され、色順応補正を素直に乗せられる。実績あり |
| CIELCh | 有力 | CIELAB の円筒座標。無彩色/有彩色のゲートと、金の彩度分離を明示的に書ける |
| OKLab / OKLCh | 有力 | 色相直線性が目的で設計されており、CIELAB の青〜紫の色相歪みを避けられる。`culori` に同梱 |
| rg 色度（正規化 RGB） | 保留 | 強度に不変なので円筒の陰影に強いが、無彩色 4 色が 1 点に潰れるため単独では使えない |
| HSV / HSL | 不採用 | 知覚的に不均等で、S が明度に汚染される。ゲート用途なら CIELCh の C\* で足りる |
| CAM16-UCS | 不採用 | 理論的には最良（視環境モデルを持つので露出変化に強い）だが `culori` に無い。自前実装はリアルタイム性と保守コストに見合わない |

## 5. 検討した色差指標

`culori` v4.0.2 が提供するもののうち、追加依存なしで使えるものを対象にした。

| 指標 | 評価 | 備考 |
| ------ | ------ | ------ |
| ΔE2000（現行） | **継続** | 「ほぼ同じ色の識別限界」用の指標。彩度補正項 S\_C が高彩度域の差を圧縮するが、実写では下記のとおり最も無難 |
| HyAB | **不採用** | 明度は絶対値、色味はユークリッドで足す混成距離。基準色どうしの余裕は広がるが、**実写で ΔE2000 より悪い**（§5.3） |
| CIE76 | 継続（区間切り分け） | 圧縮しないので「同じ色の区間か」の判定に適する。現行どおり |
| OKLab ユークリッド | 保留 | 実写でわずかに優位だが標本が小さく、判断できるだけの根拠がない |
| 重み付き LCh 距離 | 次善 | 無彩色ブランチで色相の重みを 0 にするなど、構造を手で入れられる |

HyAB の定義は次のとおり。明度差を絶対値で、色味差をユークリッド距離で足す。

```text
HyAB(a, b) = |ΔL*| + √(Δa*² + Δb*²)
```

### 基準色どうしの分離

| ペア | ΔE00 | HyAB | CIE76 | CIELCh Δh | OKLCh Δh |
| ------ | ------ | ------ | ------ | ------ | ------ |
| 金/本体ベージュ | 13.7 | **42.3** | 35.8 | 7.8° | 13.3° |
| 黄/金 | 14.0 | **35.7** | 25.3 | 9.1° | 11.9° |
| 橙/金 | 18.3 | **35.8** | 33.5 | 24.0° | 31.4° |
| 青/紫 | 14.6 | **27.9** | 23.3 | 18.0° | 40.6° |
| 茶/赤 | 21.9 | **60.7** | 47.5 | 23.0° | 25.1° |
| 赤/橙 | 29.3 | **57.9** | 42.0 | 26.6° | 28.8° |
| 茶/橙 | 38.4 | **77.3** | 54.7 | 3.6° | 3.7° |
| 黒/茶 | 24.3 | **54.5** | 41.7 | — | — |
| 白/銀 | 12.1 | **18.8** | 18.8 | — | — |
| 灰/銀 | 18.9 | **23.3** | 23.3 | — | — |

要点:

- **HyAB は紛らわしい有彩色ペアの余裕を軒並み 2〜3 倍に広げる。**
  最大は金/本体ベージュの 13.7 → 42.3（3.1 倍）で、これは
  「金バンドが本体に吸収される」既知の症状（[07](07-色帯読み取りの改善.md) 原因 ⑧）に直接対応する
- **白/銀・灰/銀は、どの指標でも最も詰まったまま。** 金属光沢は色ではないので、
  色差指標の選択では解けない。ここは別の手当てが要る（§6 も参照）
- **OKLCh は青/紫の色相差を 18.0° → 40.6° と 2.3 倍に広げる。**
  CIELAB の青領域の色相歪みが実際に効いていることの裏付け。
  金/本体ベージュも 7.8° → 13.3° と広がる

### 5.3 実写での比較 — 基準色の余裕は当てにならなかった

上の表は**基準色テーブルどうし**の幾何であって、実写の当てはまりではない。
`MANIFEST.json` でバンド列が確定している 4 枚のうち、
ラン数が正解本数と一致する 3 枚（05・23・39、計 15 バンド）について、
本番条件のランを各指標で最近傍分類した結果:

| 指標 | バンド単位の的中 | |
| ------ | ------ | ------ |
| ΔE2000（現行） | **10 / 15** | 67% |
| HyAB | 9 / 15 | 60% |
| OKLab ユークリッド | 11 / 15 | 73% |

**HyAB は基準色間の余裕を 2〜3 倍に広げるのに、実写では現行より悪い。**

理由は `calibration.txt` の「現在の Lab」対「実写の Lab」を見ると分かる。
**実写は軒並み低彩度**で、基準色テーブルが彩度過剰:

| 色 | 既定 | 実写 |
| ---- | ---- | ---- |
| 青 | L34 a29 b-61 | L43 a-6 b-16 |
| 紫 | L39 a39 b-41 | L51 a12 b7 |
| 赤 | L43 a63 b45 | L44 a36 b26 |
| 緑 | L51 a-48 b34 | L43 a-20 b24 |

基準色の彩度が実物と違うのだから、**彩度方向の差を強調する指標に変えると
誤差のほうが増幅される**。HyAB が負けるのはこのため。
**問題は指標ではなくパレット**、というのがこの測定の含意。

> **標本の小ささに注意**: 3 枚 15 バンドしかなく、しかもこの palette は
> ΔE2000 の下で学習された中央値なので、比較は構造的に ΔE2000 有利に偏る。
> 「HyAB が明確に劣る」とまでは言えないが、**「HyAB にすれば直る」という
> 当初の見立ては否定された**。指標を本気で比較するなら、
> 指標ごとに較正をやり直す閉ループが必要（§7）。

### スケールの注意

HyAB は ΔE00 のおおむね 2 倍の値域になる。指標を差し替えるなら、
**ΔE スケールに依存するハードコード定数をすべて再スケールしないと閾値が一律に緩くなる**。
該当するもの:

- `core/value/jointDecode.ts`: `CANDIDATE_DELTA_MARGIN`、`CONFIDENCE_DELTA_CEILING`、
  `DROP_COST_SCALE`、`SNAP_COST_SCALE`
- `core/bands/classify.ts`: `MAX_ACCEPTABLE_DELTA_E`
- `core/learning.ts`: `MAX_REFERENCE_DRIFT`
- `core/bands/runs.ts` / `segment.ts`: `edgeDeltaE` / `clusterDeltaE` / `mergeDeltaE`
  （こちらは CIE76 のままなら影響なし）

## 6. 不採用にした案

いずれも既に検討済み・実測で否定済みのもの。**繰り返さないこと。**

- **複数の距離指標の多数決** — [04](04-色判定方式の検討.md) §4 で却下。
  誤差源が同一の 1 画素 RGB なので誤りが独立せず、全指標が同じ方向に間違える
- **RGB ユークリッド距離** — [04](04-色判定方式の検討.md) §3 で却下。
  知覚的に不均等、明度と色味が絡む、WB ずれに弱い
- **列内分散・金属光沢で金銀を判別** — [07](07-色帯読み取りの改善.md) で実測失敗。
  σ が金 8.5〜13.9・本体 6.1〜18.9 で重なる。
  現状 `core/bands/profile.ts` は列内のばらつきを保持していないが、
  保持するよう改造しても、この用途では効かないことが分かっている
- **色順応補正を切って絶対 Lab で分類** — 39 枚の一致が 30 → 13 枚に激減。
  相対分類は必須（`core/settings.ts` の `ADAPT_WHITE_BALANCE`）
- **`profile.ts` に飽和画素ガードを入れる** — 本番条件では飽和列が 38/39 枚で 0 件。
  入れても 1 列しか変わらない（§1）
- **`adaptToAnchor` の出力で L\* を 100 にクランプする** — 誤答が 1 → 2 に増える。
  加えて金の誤学習ガード（ずれ 60.07 対 閾値 60）を無効化しかねない（§1）
- **L\* の乗算を線形輝度空間での補正に置き換える** — 理論的には正しいが 28 → 25 に悪化。
  `sample/palette.json` がこの乗算変換の下で学習されているため（§1）
- **HyAB への差し替え** — 基準色間の余裕は 2〜3 倍に広がるが実写では現行より悪い（§5.3）

## 7. 結論 — 色差指標の差し替えは優先度が低い

採否の基準は [04](04-色判定方式の検討.md) §6 に従い、
**正答率だけでなく「自信を持って誤読するケース」が増えていないか**で判断する。
現状の誤答 1 件を増やす変更は、正答が増えても採らない。

本番条件の基準値は `sample-detect/summary.txt` の **正解 28 / 誤答 1 / 保留 10**。

### 判定

**色差指標は ΔE2000 のまま据え置く。** 根拠:

1. §5.3 のとおり、実写では HyAB は現行より悪い。OKLab の優位は標本 15 バンドでは判断できない
2. 指標が効くのは `rankBandColors` と `matchCost` の 2 か所だけで、
   **バンド本数を決める 3 か所（`splitRuns` / `identifyBody` / `mergeAdjacent`）は
   すべて CIE76 系**。指標を変えても本数問題には一切効かない
3. 残る誤りの多くは**真値が上位 3 候補にすら入っていない**ため、
   指標の分解能を上げても届かない
4. `MAX_REFERENCE_DRIFT` / `MAX_ALIGN_COST` / `CANDIDATE_DELTA_MARGIN` と
   `sample/palette.json` の中央値はすべて「その指標で学習された palette」と一体。
   指標を変えるなら較正をやり直す閉ループが必須で、コストに見合わない

### 代わりに効くと分かったこと

測定の過程で、色空間より優先度の高い項目が判明した。詳細は別途。

| 項目 | 見込み | 根拠 |
| ------ | ------ | ------ |
| 確信度の式の見直し | +2 枚 | 05・23 は**値も色も完全に正解**なのに確信度 0.31 / 0.34 で保留。`jointDecode.ts` の絶対 ΔE 項が、青ボディで一様に底上げされた ΔE を過小評価する |
| `align.ts` にバンドスキップを許す | 較正データの質 | 金が本体に吸収されてランが無いのに必ず割り当てるため、白背景ランが金として学習される（§1） |
| `sample/labels.json` の人手ラベル | 前提条件 | 正解バンド列が確定しているのは 39 枚中 4 枚のみ。混同行列もこれが無いと作れない |
| `seriesRank` の E96 対応 | 5 バンド精密品 | `eseries.ts` の `seriesRank` は E6/E12/E24 しか見ず、E96 の正規値（2.26k など）が一律 3 ポイント不利になる |
| 青ボディ金属皮膜の較正 | 4 枚 | `BODY_SRGB` は beige/lightblue の 2 色のみ。01・05・23・39 の 4 枚が全滅し、かつこの条件のデータが palette に 1 件も入っていない自己強化ループ |

### 分割パラメータは既に平坦域
