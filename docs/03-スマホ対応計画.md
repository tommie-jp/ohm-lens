# OhmLens — スマホ対応計画

2026-07-27 作成。**計画のみ、実装は未着手。**

## 目的とスコープ

学習ループ（抵抗を映す → 値を打つ → その場で賢くなる）を**スマホ実機で
快適に回せる**ようにする。OhmLens の本来の利用シーンは「工作机でスマホを
かざす」なので、これはデバッグページの延命ではなく本番 UI（ロードマップ
Phase 1）への足場でもある。

やらないこと:

- 本番ドメインへの移行・ホスティング整備（設計メモ §8、別トラック）
- ネイティブアプリ化（PWA まで）

## 現状の整理

| 項目 | 状態 |
| ------ | ------ |
| HTTPS 配信（secure context） | ✅ `doStart.sh`（Tailscale + Let's Encrypt） |
| `requestVideoFrameCallback` | ✅ iOS Safari 15.4+ / Android Chrome 対応済み |
| WB・露出ロック不可（Safari） | ✅ 織り込み済み（相対分類が主防御） |
| HEIC 読み込み | ✅ 実装済み（**iPhone 実機では未検証**） |
| ビューポート設定 | ✅ `width=device-width` 済み |
| レイアウト | ❌ デスクトップ前提（幅広テーブル、小さいボタン） |
| タッチ操作 | ❌ canvas ドラッグとスクロールが競合するはず |
| 実機性能 | ❓ 8fps・800px の解析がスマホ CPU で回るか未計測 |
| ライブプレビュー | ❌ 解析フレームの貼り直し（8fps のカクつき） |

## Phase M0: 実機スモークテスト（最初にやる）

**計測せずに最適化しない。** `./doStart.sh` の URL を iPhone Safari と
Android Chrome で開き、以下を記録する。

- [ ] カメラ許可 → 映像 → 検出枠の表示まで通るか
- [ ] 解析 1 フレームの処理時間と実効 fps（**先に簡易 FPS 表示を足す**。
      これだけは M0 の前提実装）
- [ ] 発熱・電池の体感
- [ ] 値入力 → 学習 → localStorage 永続化（リロード後も残るか）
- [ ] 写真読み込み 3 経路: その場で撮影 / ギャラリー / HEIC 原本
- [ ] クリップボードコピーの可否（iOS はジェスチャ制約が厳しい）
- [ ] タブ切替・スリープ復帰後にカメラが再開するか
- [ ] 縦持ち・横持ちでのレイアウト崩れ

結果を本ドキュメントに追記し、M1 以降の優先度を決める。

## Phase M1: モバイルレイアウト

縦一列のカード構成に再編する。優先順位（上から）:

1. カメラ / プレビュー（画面幅いっぱい）
2. **読み取り結果**（大きく表示、スクロールしても見える sticky）
3. 値で学習（入力 + 学習ボタン）
4. 詳細（バンド表・1D プロファイル・正解ラベル）は `<details>` で折りたたみ

- タップターゲットは 44px 以上
- 値入力は `enterkeyhint="done"`。`4.7k` 形式なので inputmode は text のまま
- 学習ボタンは画面下部の固定バー（親指圏）に置く

## Phase M2: タッチ操作と細部

- `#source-canvas` に `touch-action: none`（ROI ドラッグとページスクロール
  の競合解消。pointer events 自体は実装済み）
- クリップボード失敗時のフォールバック（選択可能なテキスト表示に切替）
- Screen Wake Lock API で画面消灯を防ぐ（Safari 16.4+。失敗しても無視）
- `visibilitychange` でカメラの停止・再開を扱う（iOS はタブ切替で
  ストリームが止まる）

## Phase M3: 性能（M0 の実測に基づく）

8fps が維持できない場合の手当て。順に軽い方から:

1. **適応スロットリング** — フレーム処理時間を測り、間に合わなければ
   解析 fps と解像度を自動で落とす
2. **Worker 化** — ロードマップ Phase 1 の前倒し。core/ は DOM 非依存に
   保ってあるので移設は素直（`createImageBitmap` → transfer は設計済み）。
   UI スレッドのジャンクが消える

## Phase M4: ライブプレビューとオーバーレイ（Phase 1 と合流）

現在は「解析済みフレームを canvas に貼り直す」ため 8fps でカクつく。
本来の構成に切り替える:

- `<video>` を直接表示（60fps のなめらかなプレビュー）
- その上に `position: absolute` の canvas で検出枠・読み値を重ねる
- 座標変換（video 内在解像度 ↔ CSS 表示座標）を一箇所に集約
  （設計メモ §2 [6] の注意そのまま）
- 検出枠の時間平滑化（数フレームの移動平均）。手持ち撮影のブレで
  枠が暴れるのを抑える — Phase 2 のトラッキングの簡易版

## Phase M5: PWA 最小対応（任意）

- manifest + アイコンで「ホーム画面に追加」できるようにする
- オフラインキャッシュはロードマップ Phase 4 で本格対応（今回はスコープ外）
- **注意**: 権限・ストレージはオリジン単位（設計メモ §8）。`*.ts.net` の
  URL で PWA 化しても本番ドメインには引き継げない。暫定と明記して運用する

## リスク

| リスク | 備え |
| -------- | ------ |
| iOS のメモリ制限（HEIC WASM 3MB + 高解像度画像）でタブが落ちる | M0 で確認。落ちるなら HEIC 変換後に即解放・画像の縮小を前倒し |
| 手持ち撮影のブレで自動検出が暴れ、学習の対応付けが不安定 | M4 の平滑化を前倒しするか、「この画で止める」を学習の推奨経路にする |
| iOS Safari の getUserMedia がジェスチャ文脈以外で失敗 | カメラ開始は必ずボタンタップから（現状の構成で満たしている） |
