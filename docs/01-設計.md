# OhmLens — 設計メモ

Webカメラに映した抵抗器の抵抗値を、リアルタイムで映像にオーバーレイ表示するWebアプリ。

> 2026-07-27: ライブラリ選定・アーキテクチャの検証レビューを反映（WB ロックの
> Safari 非対応対策、OpenCV.js 依存の再考、YOLO26 NMS-free、E系列スナップ順序、
> WebGPU Baseline 到達）。

- **プロジェクト名**: OhmLens
- **当面のURL**: `https://ohmlens.tommie.jp`
- **リポジトリ / パッケージ名**: `ohm-lens`
- **方針**: ブラウザ完結（クライアントサイド推論）、サーバ不要

---

## 1. アーキテクチャ

### 基本方針：ハイブリッド2段パイプライン

「**NNで位置を検出** → **古典CVで色帯を読む**」の二段構え。カラーバンド読み取りまでNNに任せると学習データが膨大に必要になり、誤読時のデバッグが不可能になる。値の算出を決定的アルゴリズムにすることで、精度とデバッグ性を両立する。

### 処理フロー

```text
getUserMedia
  └→ requestVideoFrameCallback でフレーム取得
      └→ createImageBitmap → Worker へ transfer
          ├→ [1] 物体検出   : ONNX Runtime Web + YOLO(OBB)
          ├→ [2] 回転補正   : OpenCV.js warpAffine
          ├→ [3] 色帯解析   : Lab + ΔE2000 最近傍
          └→ [4] 値の確定   : 方向判定 → E24/E96 スナップ
              └→ postMessage でメインスレッドへ
                  ├→ [5] トラッキング : IoUマッチング + 時間方向多数決
                  └→ [6] 描画        : <video> + 重ねた <canvas>
```

### スレッド分離

| スレッド | 担当 | 頻度 |
| --- | --- | --- |
| メイン | 映像表示、Canvasオーバーレイ、トラッキング | 60fps |
| Worker | 物体検出、色帯解析 | 5〜10fps |

検出フレーム間はトラッカーの予測位置でラベルを補間すると滑らかに見える。

## 2. 各工程の詳細

### [0] 映像取得

```js
const stream = await navigator.mediaDevices.getUserMedia({
  video: { facingMode: 'environment', width: { ideal: 1920 } }
});
```

- フレーム同期は `video.requestVideoFrameCallback()` を使う。`setInterval` / `requestAnimationFrame` より正確で無駄がない。rVFC は Firefox 132+ を含む全主要ブラウザで利用可（[caniuse](https://caniuse.com/mdn-api_htmlvideoelement_requestvideoframecallback)、2026-07確認）。
- `MediaStreamTrackProcessor` + `VideoFrame` で完全にWorkerへオフロードする手もあるが、[MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrackProcessor) 上でも "This feature is not Baseline because it does not work in some of the most widely-used browsers." という状態でDedicated Worker限定。移植性を考えると rVFC + `createImageBitmap()` の transfer が無難。
- **カメラ設定の固定は「できる環境でのみ」の最適化**。`track.applyConstraints()` の `whiteBalanceMode` / `exposureMode: 'manual'` は **Chromium 系限定**で、Safari（macOS / iOS）は ImageCapture 系制約に未対応（2026-07確認）。iPhone では WB ロックができないため、**これを前提に色判定を設計しない**。
  - 主防御は [3] の**フレーム内基準色に対する相対分類**とする。WB ロックが効く環境では併用してさらに安定させる。

### [1] 物体検出

- **Ultralytics YOLO**（nanoサイズ、yolo11n / yolo26n）を ONNX エクスポート → **onnxruntime-web** で推論。
- **OBB（回転バウンディングボックス）タスクを使うこと**。抵抗器は細長く斜めに置かれるため、軸平行ボックスだと隣の抵抗器やリード線を巻き込んで色帯解析が破綻する。OBBなら角度がそのまま次段の回転補正に使える。
- **YOLO26 なら NMS 不要**。YOLO26 はエンドツーエンド（NMS-free、DFL 廃止）設計のため、出力デコードが単純になる。yolo11n-obb を使う場合のみ自前 NMS が必要。
- Execution Provider は `['webgpu', 'wasm']` の順でフォールバック。WebGPU は 2026-01 に全主要ブラウザで Baseline 到達（Safari 26 / Firefox 141+ で default on）済みのため、WASM フォールバックの出番は当初想定より少ない。
- モデルは fp16 / int8 量子化して数MBに収める。
- ONNX エクスポート時の opset は WebGPU EP との相性問題の報告があるため、エクスポート後に **webgpu / wasm 両方の EP で動作確認**する。

### [2] / [3] 回転補正と色帯解析

1. OBBの角度で回転切り出し → 抵抗器を水平化
2. 長軸方向に中央付近の複数行をサンプリング、**中央値**で1Dカラープロファイル化（ノイズ低減）
3. **Lab色空間**に変換し、基準色との **ΔE（CIEDE2000）最近傍**で分類
4. 本体色（ベージュ／水色）を背景として除去 → 連続ランのラベリングでバンド抽出

> HSVだけでは茶／赤／橙、金／黄の区別が実用に耐えない。Lab + ΔE2000 が必須。

**ROIは高解像度フレームから切り出すこと。** 推論は640pxにダウンスケールしてよいが、色帯は細いので解析は元解像度で行う。

#### 相対分類（WBロック不可環境への主防御）

Safari では WB ロックができない（[0] 参照）ため、絶対 Lab 値との ΔE ではなく
**フレーム内の基準色に対する相対分類**を主防御にする。

- 抵抗器の**本体色（ベージュ／水色）は毎フレーム確実に取れる**ので、これを
  白色点補正のアンカーに使う
- 「この枠に置いてください」の UI ガイド枠内に白基準（白い紙）を要求すれば、
  von Kries 型の簡易色順応補正が安定して掛けられる
- WB ロックが効く Chromium ではロックを併用してさらに安定させる

#### OpenCV.js は使わない方向で検討

この工程で OpenCV.js に頼るのは実質 `warpAffine`（回転切り出し）だけ。
1関数のために 8〜10MB の WASM を積むのは重い。

- 回転切り出しは `OffscreenCanvas` 2D の `setTransform` → `drawImage` で
  20行程度・GPU支援付きで書ける
- 中央値プロファイル化・連続ランのラベリングは元々自前ループ
- **Phase 0 では実験の速さ優先で OpenCV.js を使ってもよいが、Phase 1 以降に
  持ち込まない**

### [4] 方向判定と値の確定

- 金／銀の許容差バンドがある側を末尾とみなす
- なければ両端の余白比率で判定（許容差バンド側は間隔が広い）
- 4／5／6バンドに対応
- 最後に **E24 / E96 系列にスナップ**して妥当性チェック → 1バンドの誤読を弾ける
- **スナップの順序**: 許容差バンドで系列を先に決める（金=±5%→E24、茶=±1%→E96）。
  E24+E96 の和集合にスナップすると格子が細かすぎて誤読棄却の効果が薄れる

### [5] トラッキング（体感品質を最も左右する）

- IoUベースの簡易トラッカー（自前30行程度、SORT相当）で各抵抗器にIDを付与
- OBB同士の厳密な回転IoUは重い。対象はほぼ静止物なので、マッチングは
  **中心点距離**で十分
- IDごとに直近10〜20フレームの結果を**多数決**
- 単フレーム精度80%でも、時間方向の投票で表示は95%以上に安定する
- 確信度が閾値未満なら値を出さず「?」を表示する

### [6] オーバーレイ描画

- `<video>` の上に `position: absolute` の `<canvas>` を重ねるのが基本
- テキストラベルだけ絶対配置のDOM要素にして `transform: translate()` すると、フォントが綺麗でクリック操作も付けやすい
- `object-fit: cover` は映像の内在解像度とCSS表示サイズがズレる。**座標変換関数は必ず一箇所にまとめる**

## 3. ライブラリ選定

| 用途 | 採用 | 備考 |
| --- | --- | --- |
| 映像取得 | WebRTC `getUserMedia` / `requestVideoFrameCallback` | 標準API |
| 推論 | **onnxruntime-web** | v1.27.0（2026-06時点）。WebGPU EP がデフォルトGPU EP。WebNN はまだ実験段階 |
| 古典CV | **@techstark/opencv-js**（Phase 0 限定の暫定） | v5.0.0-release.1。実質 warpAffine のみの利用なので Phase 1 以降は OffscreenCanvas 2D で代替し依存を外す（§2 [2]/[3] 参照） |
| モデル学習 | **Ultralytics YOLO** (detect / obb) | ONNXエクスポートで約43%高速化と公称。YOLO26 は NMS-free |
| アノテーション | Roboflow / Label Studio / CVAT | |
| 色差計算 | `culori` | v4.0.2。`differenceCiede2000` / `modeLab` あり。`culori/fn` で tree-shaking 可、数KB |
| UI | React or Svelte | 描画はCanvas 2Dで十分、大量なら PixiJS |
| トラッキング | 自前IoU実装 | 外部ライブラリ不要 |

### 採用しない選択肢

- **サーバ推論（WebRTC送信 + Python）**: 精度は最高だがレイテンシ・コストが乗り、オフラインで動かない。この用途はクライアント完結が明確に有利。
- **VLM（GPT-4o / Claude vision）を本番ループに**: リアルタイム性とコストで不向き。ただし**学習データの自動ラベリング**や難ケースのオフライン検証には非常に有用なので、開発ツールとしては使う。

## 4. 学習データ

- 自前撮影 **300〜500枚**程度から実用レベルに届く
- 重要なのは augmentation：**照明色温度・ホワイトバランス・露出・回転・ぼけ**を強めにかける
- Roboflow か Label Studio でアノテーション

## 5. 精度の落とし穴

- 金属皮膜抵抗の**青ボディは白／銀バンドのコントラストが低い**
- 光沢ボディは**鏡面反射**で色が飛ぶ → 拡散照明を促すUIガイド（「この枠に置いてください」）を出すだけで実効精度が大きく変わる
- 実物でも紛らわしい色（茶／赤／橙、金／黄）が存在する
- **候補トップ1だけでなく、上位候補と確信度を併記**するとユーザーが自分で判断でき、実用性が上がる

| 0 | 静止画1枚をOpenCV.jsのみで処理（白背景・水平配置前提） | 色帯読み取りロジックを完成させる |

## 8. ホスティング（ohmlens.tommie.jp）

### オリジンは後から変えると痛い

カメラ許可・PWAインストール状態・localStorage・Service Workerキャッシュは**すべてオリジン単位**。後で独自ドメインへ移行すると、許可プロンプトが出し直しになり、ホーム画面アイコンは古いオリジンを指したままになる。

- 本気で育てるなら → 最初から独自ドメイン、サブドメインは開発／ステージング用
- まず反応を見る段階 → サブドメインで問題なし。移行時に301リダイレクトを張る前提でパス設計をシンプルに保つ

### 必須ヘッダ

`getUserMedia` も WebGPU も secure context 必須（HTTPSであればサブドメインで問題なし）。

さらに **cross-origin isolation** を張ると `SharedArrayBuffer` が使え、WASMバックエンドのマルチスレッドが有効になる（WebGPU非対応環境で推論速度が数倍変わる）。

```text
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  Permissions-Policy: camera=(self)
```

> ⚠️ これを有効にすると、外部の埋め込みやGoogle Fontsが `crossorigin` 属性やCORPヘッダなしでは読めなくなる。**外部リソースは全て自ホストに寄せるのが結局楽。**
>
> ⚠️ **GitHub Pagesではカスタムヘッダを設定できない**のでcross-origin isolationが張れない。Cloudflare Pages / Netlify / Vercel / 自前Nginx なら設定一行。tommie.jp の現在の基盤で対応可能か先に確認すること。

### 配信最適化

- ファイル名にコンテンツハッシュ → `Cache-Control: public, max-age=31536000, immutable`
- `.wasm` は `application/wasm` の MIME タイプで返す
- Brotli 圧縮を有効化（ONNXモデルは効きにくいので、サイズ削減は量子化で行う）

### サブドメインの利点

kick.tommie.jp と Cookie・ストレージが完全分離される。カメラという強い権限を要求するアプリを既存サイトと同居させないのは、セキュリティ的にもユーザーの心理的にも正しい判断。

## 9. 実装スケルトン

```js
// worker.js
import * as ort from 'onnxruntime-web/webgpu';

const session = await ort.InferenceSession.create('/models/resistor-obb.onnx', {
  executionProviders: ['webgpu', 'wasm'],
  graphOptimizationLevel: 'all',
});

self.onmessage = async ({ data: { bitmap, frameId } }) => {
  const input = preprocess(bitmap, 640);       // letterbox + NCHW正規化
  const out   = await session.run({ images: input });
  const boxes = decodeOBB(out, 0.45);          // YOLO26ならNMS不要（yolo11nなら自前NMS）

  const results = boxes.map(b => {
    const roi   = cropRotated(bitmap, b);      // OffscreenCanvas 2Dで水平化（高解像度側から切る）
    const bands = readColorBands(roi);         // Lab + ΔE2000（本体色アンカーで相対分類）
    return { box: b, ...bandsToOhms(bands) };  // { ohms, tolerance, confidence }
  });

  self.postMessage({ frameId, results });
  bitmap.close();
};
```

メインスレッド側は `requestVideoFrameCallback` で `createImageBitmap(video)` を作って transfer し、返ってきた結果をトラッカーに通して描画するだけ。
