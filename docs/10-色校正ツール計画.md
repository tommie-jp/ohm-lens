# OhmLens — 色校正ツール計画

2026-07-28 作成。`doDetect.sh` の結果を Web ページとして出し、**検出した色と
バンド数を人手で訂正**して、その結果を基準色パレットへ還元するまでの計画。

> **要点: 作りたいループの大半は既に実装済みで、切れているのは `labels.json`
> の前後だけ。** 新しい校正系を並行して作らず、既存の輪を閉じる。
>
> - `sample/palette.json` → 検出、の経路は既に通っている（`scripts/detect.ts`）
> - `sample/labels.json` は**誰も書かず誰も読まない**まま残っている
> - `MANIFEST.json` の `bands` に正解の器はあるが **39 枚中 4 枚しか埋まっていない**

## 1. 何を作るのか

```text
sample/*.jpg
   ↓ doDetect.sh（検出）
sample-detect/*.html + *.json     ← 人がブラウザで見る
   ↓ 人が本数と色を訂正 → サーバへ保存
sample/labels.json                ← 訂正の正
   ↓ calibrate.ts（集計）
sample/palette.json               ← 基準色。既に detect.ts が読んでいる
   ↓
次回の doDetect.sh
```

人が直すのは「この帯は red」「本数は 4 本」という**ラベル**であって、Lab の
数値ではない。Lab は観測の中央値として機械が導く派生物。ここを混ぜると
再検出のたびに整合性が取れなくなる。

## 2. 確定した設計判断

| 論点 | 決定 |
| ------ | ------ |
| 訂正の保存経路 | **サーバ**（`./doDetect.sh --serve` が立てる小さな node サーバ） |
| 訂正の正 | `sample/labels.json`（ツール書き込み専用） |
| `MANIFEST.json` の `bands` | `labels.json` へ移行して**削除**（同じ事実を 2 箇所に置かない） |
| localStorage | **下書きバッファのみ**。サーバが正。未送信分の退避に限る |
| バンド列の並び順 | **写真順**（ROI 長軸の昇順）。読み向きは `readDirection` で別に持つ |
| 訂正の主操作 | **本数セレクタ → 候補導出 → 確定**。色の手動指定はフォールバック |
| 検出への帰還 | `palette.json` のみ。**本数・色列は検出経路に渡さない** |
| 出力 | `sample-detect/` に静的 HTML + JSON。`summary.txt` は残す |

保存経路をサーバにしたことで、「localStorage とファイルのどちらが勝つか」の
優先順位問題は消える。タイムスタンプ突き合わせは不要。

### 2.1 所有者でファイルを分ける

| ファイル | 所有者 | 内容 |
| ---------- | -------- | ------ |
| `MANIFEST.json` | 人（手編集） | 出典・ライセンス・期待値・撮影メモ |
| `labels.json` | ツール（サーバ書き込み） | 訂正した本数・色列・読み向き |
| `palette.json` | ツール（生成物） | 集計した基準色 Lab |

`MANIFEST.json` は出典とライセンスを持つ台帳なので、サーバプロセスに書き戻させ
ない。クロバー事故と diff の汚れを避ける。

## 3. 人手校正の対象を絞る

`calibration.txt` を見ると 39 枚中 30 枚は既に自動で対応付いている。残り 9 枚は
性質が 2 種類に分かれ、打ち手が違う。

| 症状 | 枚数 | 本体 | 色名訂正で直るか |
| ------ | ------ | ------ | ------------------ |
| `コスト N が高すぎる`（01 / 05 / 09 / 19 / 26 / 38） | 6 | 色の解釈が誤り | **直る見込み** |
| `ラン 9 本、対応付け不可`（07 / 16 / 21） | 3 | 分割が壊れている | **直らない** |

後者に対して「色名プルダウン」だけの UI を作ると、一番直したい画像で手が出せ
ない。**UI には「このランはバンドではない」を落とす操作と、「検出に無いバンドを
足す」操作を必ず入れる。**

`MANIFEST.json` に期待値がある以上、成功している 30 枚は人間が触る必要がない。
一覧ページは**要校正だけを既定表示**にする。

## 4. データ形式

### 4.1 `sample/labels.json`

```json
{
  "11-220ohm-5pct.jpg": {
    "bandCount": 4,
    "readDirection": "ltr",
    "bands": [
      { "color": "red",   "center": 0.22 },
      { "color": "red",   "center": 0.38 },
      { "color": "brown", "center": 0.54 },
      { "color": "gold" }
    ],
    "updatedAt": "2026-07-28T12:00:00Z"
  }
}
```

- `bandCount` — 実物に印刷されている帯の本数（3〜6）。**必須**
- `bands` — **任意**。あれば `length === bandCount` を検証する
- `center` — **任意**。ROI 長軸の正規化位置 [0, 1]
- `readDirection` — `ltr` / `rtl`。写真上で左右どちらから読むか

`bandCount` は `bands.length` から導けるが、あえて独立に持つ。「5 本ある」とは
分かるが全色を自信をもって言えない段階が実在し、そこで作業を止めたくないため
（§5 の二段階運用）。両方あるときの不整合はサーバが弾く。

### 4.2 訂正には 2 種類あり、消費先が違う

| 種類 | `center` | palette 学習 | 本数一致率・回帰 |
| ------ | ---------- | -------------- | ------------------ |
| 色名の変更、ランのノイズ除外 | あり | **使える** | 使える |
| 検出に無いバンドの追加 | なし | 使えない | 使える |

金帯が本体ベージュに埋もれて検出から消えるのは既知の問題
（`core/learning.ts` の `ValueMatch.toleranceObserved` のコメント）。人が
「ここに金が 1 本ある」と足しても対応するランが無く、Lab のサンプルは取れない。
`center` を任意にしておけば 1 ファイルで両方を持てる。集計側は `center` の
あるものだけ拾う。

### 4.3 並び順の規約（罠）

**写真順で保存する。** 写真順 = `rectify` 後の ROI 長軸で左→右、検出結果の
ラン `start` 昇順と一致する順序。

現状の `MANIFEST.json` 01 番はこの規約に**反している**。

```json
{ "note": "写真では抵抗が逆向き（バンドは右から左に読む）",
  "bands": ["brown", "black", "black", "silver", "brown"] }
```

`brown black black` = 100、`silver` = ×0.01 → 1Ω、`brown` = ±1% と、そのまま
デコードできる並びで入っている。つまり**読み順**で保存されている。写真順なら
`brown silver black black brown` になるはず。

読み順で保存してはいけない理由は 2 つ。

1. 人は写真を見たまま左→右で入力する。読み順に直させると入力ミスの温床になる
2. `core/value/direction.ts` が向きを判定している以上、**向き判定の正誤も評価
   対象**。読み順で保存すると向きの正解が消え、評価できなくなる

移行時、既存 4 件は単純コピーでは済まない（§8 Phase 3）。

### 4.4 検出結果 JSON（`sample-detect/<name>.json`、毎回生成）

```json
{
  "file": "11-220ohm-5pct.jpg",
  "image": { "width": 800, "height": 600 },
  "box": { "cx": 0, "cy": 0, "length": 0, "thickness": 0, "angleDeg": 0 },
  "runs": [
    { "index": 0, "start": 0.18, "end": 0.26, "center": 0.22,
      "lab": { "l": 0, "a": 0, "b": 0 }, "color": "red",
      "role": "数字", "dropped": false }
  ],
  "reading": { "ohms": 220, "confidence": 0.83, "confident": true },
  "expected": { "ohms": 220, "tolerance": 5 },
  "status": "ok"
}
```

`start` / `end` / `center` は ROI 長軸の**正規化値**に統一する。これが
`labels.json` の `center` と同じ土俵に乗るための前提。

## 5. 訂正 UI を反転させる

`expected.ohms` と `tolerance` は 39 枚すべてにある。`core/learning.ts` の
`expectedSequences(ohms, tolerance)` は候補列を列挙するが、2 桁系と 3 桁系の
両方を返すので絞れていない。**本数を与えると長さフィルタでほぼ一意に決まる。**

220Ω ±5% + 本数 4 → `red-red-brown-gold` の一択。

```text
本数 [3][4][5][6] → 4
        ↓ expectedSequences(220, 5, 4)
候補   red-red-brown-gold        [確定]
```

主操作は「色を 1 本ずつ選ぶ」ではなく「本数を選んで確定する」。39 枚を回すなら
ここが速度のすべてになる。色の手動指定は候補が出ないときのフォールバック。

`core/value/decode.ts` の `digitCountFor()` が既に本数→桁数の対応を持っている
ので、この写像はコード側にもある。

**二段階運用**:

1. **1 周目** — 39 枚の `bandCount` だけ直す。プルダウン 1 つなので数分
2. **2 周目** — それでも読めない画像だけ `bands` を埋める

`bandCount` 単独でも本数一致率（§7）が回り、`bands` が埋まって初めてパレット
学習に効く、という段階差をそのまま表せる。

**既知の穴**: 6 本（温度係数付き）は `expectedSequences` が生成しない。4 本でも
「3 桁＋倍率、許容差なし」の精密品があり得る。候補ゼロ件なら手動入力へ落とす。

## 6. 漏洩の境界（最重要）

本数を `refineBoxExtent` に渡せば、その画像の検出は確実に良くなる。カラーコード
の規格（3〜7 本・等間隔）で枠を伸ばす実装が既にあるので、渡せば効く。

**これをやると評価が無意味になる。**

| 経路 | 正解を使ってよいか |
| ------ | -------------------- |
| 検出経路（`locateResistor` / `refineBoxExtent` / `analyzeRoi` / `decode`） | **不可** |
| 学習経路（`matchRunsToValue` / `calibrate.ts`） | 可。それが学習だから |
| 検出へ戻してよい成果物 | `palette.json` のみ（全画像から導いた画像非依存の基準色） |

`doDetect.sh` が `labels.json` を直読みしてもいけない。直読みすると「その画像
だけ正解を知っている」状態になり、精度の数字が意味を失う。必ず `palette.json`
への集計を挟む。

切り分けのために答えを教えたいときは `--oracle` のような明示フラグにし、
`summary.txt` に「答えを教えた実行」と刻む。

それでも 39 枚で校正して同じ 39 枚で評価する構図は残る。**summary には
「学習込みの数字」と明記する。**

## 7. 得られる新しい評価軸

本数の正解が入ると、**セグメンテーションの失敗と色命名の失敗を分離**できる。

```text
処理 39 枚 / 検出成功 35 / 本数一致 28 / 色列一致 24 / 向き一致 37 / 値一致 22
```

現状の `コスト 30.3 が高すぎる` より遥かに行動に結びつく。本数が合っていて色が
違うならパレットの問題、本数から違うならランの問題。一覧ページのフィルタも
この軸で切る。

## 8. フェーズ

### Phase 0 — 形式を決める

**成果物**: 本書。

§4 のスキーマ、§4.3 の並び順規約、§6 の漏洩境界を確定させる。あわせて
`CLAUDE.md` の「ブラウザ完結・サーバを持たない」は**アプリ本体**の制約であり、
開発用校正ツールは対象外である旨を明記する。

### Phase 1 — 検出結果を JSON で出す

**触る**: `src/annotate/pipeline.ts`、`scripts/detect.ts`

- `annotateImage()` が `jpeg` / `caption` に加えて構造化結果を返す
- ランの `start` / `end` を ROI 長軸の正規化値に統一（後続すべての土台）
- `detect.ts` が `<name>.json` を書く
- **画像焼き込みは据え置き**。回帰の有無を `summary.txt` で確認できる状態を保つ

**検収**: 既知 3 枚で JSON スナップショット。既存の `summary.txt` が 1 バイトも
変わらないこと。

ここで止まっても損はない。JSON があるだけで `dbgRuns.ts` 相当の調査が楽になる。

### Phase 2 — 静的ページ生成（読み取り専用）

**新規**: `scripts/report.ts`

```text
sample-detect/
  index.html              一覧・状態フィルタ
  assets/app.js  app.css  全ページ共通（ロジックはここだけ）
  11-220ohm-5pct.html     <script>window.DETECTION={...}</script> のスタブ
  11-220ohm-5pct.json
  summary.txt
```

- 画像は `../sample/xx.jpg` を相対参照する（複製しない）
- オーバーレイは `src/annotate/render.ts` の `buildAnnotationSvg()` を再利用し、
  ブラウザで `<img>` に重ねる。座標系が同じなので変換は要らない
- **オーバーレイ ON/OFF トグル**を付ける（素の色を見たいため）
- 個別ページは薄いスタブにし、**39 ページあってもコードは 1 本**にする

**判断ポイント**: ここで一度止めて、失敗している 9 枚を目視する。**「色名の訂正
で直りそうな枚数」を実測してから Phase 3 以降に進む。** 想定より少なければ、
投資先はセグメンタ側に変わる。

`sample-detect/` が `.gitignore` 済みかをこのフェーズの前に確認する。

### Phase 3 — labels.json と保存サーバ

**新規**: `scripts/serve.ts`（`node:http` のみ、依存追加なし）

vite には相乗りしない。校正ページは `sample-detect/` の静的ファイル群でアプリ
本体とは別物であり、`public/` やビルドに混ざる事故を避ける。

```text
GET    /api/labels          labels.json 全体
PUT    /api/labels/:file    1 エントリ更新
DELETE /api/labels/:file    訂正取り消し
静的配信                     sample-detect/ と ../sample/（拡張子 allowlist）
```

**検証はサーバでやる。** UI だけの検証では、残るファイルが壊れる。

- `bandCount` は 3〜6
- `bands` があれば `length === bandCount`、色名は `BAND_COLORS` に含まれる、
  `center` は昇順かつ [0, 1]
- **デコード結果が `MANIFEST.expected.ohms` と一致する。** 不一致は 400 で理由を
  返す（人手ラベルの誤りは必ず出る）

**書き込みの作法**: temp → rename のアトミック書き込み、キー順ソートの安定整形。
外側リポジトリで追跡するファイルなので、diff が読めないと校正の履歴を追えない。
パスはリクエストから受け取らず、書き込み先は `labels.json` 固定・localhost
バインドのみ。

**移行**: `MANIFEST.json` の `bands` 4 件を `labels.json` へ。**01 番は読み順で
入っているので反転が必要**（§4.3）。単純コピー禁止、目視確認する。移行後
`MANIFEST.json` から `bands` を削除する。

`doDetect.sh` に `--serve` を追加する。

### Phase 4 — 訂正 UI

**前提となる小改修**: `expectedSequences()` に本数の任意引数を足して長さで絞る
（数行）。

- 本数セレクタ → 候補導出 → 確定（§5）
- 候補 0 件または複数 → 手動モードへ
- 手動モード: 色プルダウン / **ランをノイズとして除外** / **検出に無いバンドを
  追加**（`center` なし）
- `readDirection` トグル
- 保存はサーバへ PUT。**失敗したときだけ** localStorage に退避し、次回起動で
  再送を促す
- サーバ不在時のフォールバックとして `labels.json` ダウンロードを残す
  （作業が死なないように）

### Phase 5 — 集計 → palette.json

**新規**: `scripts/calibrate.ts`

```text
labels.json（center つきバンドのみ）
   ↓ 既定パレットでの検出結果に対して Lab をサンプル
   ↓ 色ごとに各成分の中央値
   ↓ MAX_REFERENCE_DRIFT ガード（core/learning.ts）
palette.json + 較正レポート
```

- **集計は必ず既定パレットでの検出に対して行う。** 学習パレットで検出した結果を
  学習に戻すと帰還ループになり、収束が保証されない
- `MAX_REFERENCE_DRIFT` のガードは残す。金が「L126 のほぼ白」として 15 件学習
  され読み取り全体を壊した実績がある
- `palette.json` に入力のハッシュ（`labels.json` + 既定パレット版）を記録して
  再現性を持たせる
- `doDetect.sh` は `palette.json` を読むだけなので**変更不要**。「次回から訂正を
  読み込んで実行」はこれで閉じる

既存の `calibration.txt` を置き換える。

### Phase 6 — 評価軸

- 本数一致率 / 色列一致率 / 向き一致率を `summary.txt` と `index.html` に出す
- 学習込みの数字である旨を明記する（§6）
- `core/learning.ts` の `MAX_SKIPS = 4` を、本数既知のとき
  `runCount - bandCount` の厳密値にする。緩い上限が「コスト高すぎ」の誤対応を
  生んでいる可能性がある

## 9. リスク

| リスク | 対処 |
| -------- | ------ |
| 本数を検出器に渡す誘惑（効き目が露骨） | §6 の境界。使うなら `--oracle` で明示し summary に刻む |
| 帰還ループ（学習が自分の入力を変える） | 集計は既定パレット基準。`center` は正規化位置でセグメンタ非依存 |
| 並び順の取り違え | §4.3 の規約を先に固定、移行時に既存 4 件を目視確認 |
| 人手ラベルの誤り | サーバ側でデコード整合を検証し 400 を返す |
| 39 枚の HTML で差分が汚れる | `sample-detect/` の `.gitignore` を Phase 2 の前に確認 |
| 色名訂正では直らない画像が多い | Phase 2 終了時に実測してから Phase 3 へ進む |

## 10. 検収

TDD 前提（RED → GREEN → REFACTOR、カバレッジ 80%）。

- Phase 1 / 5 / 6 はコアロジックなのでユニットテスト必須
- Phase 2 / 4 はブラウザ側なので、スキーマのユニットテスト + Playwright での
  目視確認まで
- Markdown を書いたら `npx markdownlint-cli '**/*.md'` を通す
