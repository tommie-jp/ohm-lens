## 0. 技術基盤の決定

| 項目 | 決定 | 理由 |
| ------ | ------ | ------ |
| ビルド | Vite（`vanilla-ts` テンプレート） | Phase 0 のコアロジックはフレームワーク非依存の純粋 TS。UI フレームワーク（React/Svelte）の選定は Phase 1 の UI 実装まで先送りする（YAGNI） |
| 言語 | TypeScript（strict） | |
| テスト | Vitest + @vitest/coverage-v8 | Vite と同一エコシステム。カバレッジ 80% 以上（コアロジック対象） |
| Lint | ESLint + typescript-eslint（最小構成） | |
| 依存（Phase 0） | `culori`（`culori/fn` で tree-shake）のみ | OpenCV.js は入れずに始め、回転切り出しが必要になった時点で判断（Phase 0 は水平配置前提なので不要の見込み） |

## 1.5 Phase 1 に持ち越す設計課題

コードレビュー（2026-07-27）で指摘された、Phase 0 の範囲では実害が無いが
Phase 1 で必ず効いてくる項目。着手時にここから拾う。

| 課題 | 内容 | 影響 |
| ------ | ------ | ------ |
| 本体範囲の検出 | ROI に机などの背景が入ると、(a) 端の背景列が white/grey バンドとして誤検出され、(b) 背景が過半を占めるとアンカー中央値が机の色になる。現在は「ROI ≒ 本体」を暗黙の前提にしている | **大**。Phase 1 の「中央固定 ROI」では必ず背景が入る。本体色の最長ランを検出して、その範囲だけをアンカー推定とバンド抽出の対象にする |
| 基準色テーブルの注入 | `BAND_REFERENCE_COLORS` などがモジュール定数のため、Step 0-7 の較正がソース編集になる。フィクスチャ探索の自動化ができない | **中**。`Palette` 値を引数で受け取る形にする（既定は現行テーブル） |
| 分類とセグメントの順序 | 現在は画素ごとに argmax 分類 → 色が変わったらラン分割。茶/赤のような紛らわしい色では 1 本のバンドが細切れになり `minBandWidth` で消える | **中**。先に非本体の連続ランを切り、ラン単位で 1 回だけ分類する。上位候補も `Band` に載せられる |
| 色順応アンカーの一般化 | `adaptWhiteBalance: boolean` では「本体色アンカー」しか選べない。設計メモが挙げる「UI ガイド枠内の白基準」は ROI 外にあり渡せない | **中**。`Adaptation` を直接受け取れるようにする |
| プロファイルの構造 | `ProfileSample[]`（オブジェクト配列）は 1 フレームあたり数千個の短命オブジェクトを生む。Float64Array の構造体配列にすると割り当てがほぼ消える | **小**（GC ジッタ）。`ProfileSample[]` を消費する箇所が変わるので Phase 1 の前に決める |

設計原則: `core/` は **ImageData（生ピクセル配列）だけを入力にする**。
Canvas / video / File への依存は `debug/`（と将来の UI 層）に閉じ込め、
コアを Node 上の Vitest でそのままテストできるようにする。

## 2. Phase 0 — 色帯解析コアロジック（静止画・白背景・水平配置）

**ゴール**: 白背景・水平配置で撮影した静止画から抵抗値を正しく読み取る。
**出口条件**: 自前撮影のフィクスチャ画像セット（20枚目標）で読み取り成功率 90% 以上。
カバレッジ 80% 以上。

TDD で進める（RED → GREEN → REFACTOR）。依存関係の少ない順に:

| Step | 状態 |
| ------ | ------ |
| 0-1 スキャフォールド | ✅ 完了 |
| 0-2 E系列スナップ | ✅ 完了 |
| 0-3 デコードと方向判定 | ✅ 完了 |
| 0-4 色分類 | ✅ 完了 |
| 0-5 プロファイル抽出・バンド分割 | ✅ 完了 |
| 0-6 デバッグページ | ✅ 完了 |
| 0-7 実画像フィクスチャで較正 | ⏸ 撮影画像の提供待ち |

### Step 0-1: スキャフォールド

- Vite vanilla-ts + Vitest + ESLint + `.editorconfig`
- `npm run test` / `npm run lint` / `npm run dev` が通る空の状態を作る
- CI（GitHub Actions）: push 時に lint + test + coverage

### Step 0-2: E系列スナップ（`value/eseries.ts`）— 純粋数学から着手

- テスト先行: `snapToSeries(4700, 'E24') → 4700`、`snapToSeries(4650, 'E96') → 4640` など
- 許容差バンドから系列を決定（金=±5%→E24、茶=±1%→E96）してからスナップ
- スナップ前後の乖離が閾値超過なら「誤読の可能性」フラグ

### Step 0-3: バンド列 → 値のデコード（`value/decode.ts` / `value/direction.ts`）

- テスト先行: 4/5/6 バンドの正常系・逆順・許容差バンド無しのケース
- 方向判定: 金/銀がある側を末尾 → 無ければ余白比率
- 両方向でデコードして E系列適合度で優劣を付ける（direction の補強）

### Step 0-4: 色分類（`color/` + `bands/classify.ts`）

- 基準色テーブル: カラーコード 12 色 + 本体色（ベージュ/水色）を Lab で定義
- テスト先行: 合成 Lab 値（基準色 + ノイズ）で最近傍分類を検証
- 相対分類: アンカー（本体色）で von Kries 補正してから ΔE2000
- 分類結果は色 + 距離（確信度の材料）を返す

### Step 0-5: プロファイル抽出とバンド分割（`bands/profile.ts` / `bands/segment.ts`）

- 入力は ImageData。中央付近の複数行をサンプリングし列ごとの中央値で 1D 化
- 本体色±閾値を背景として除去 → 連続ランをラベリング → 幅・位置でバンド候補化
- テスト: プログラム生成した合成プロファイル（既知のバンド配置）で検証

### Step 0-6: デバッグページ（`debug/`）

- 画像アップロード → ROI を手動矩形指定（Phase 0 は検出なしなので手動）
- 各段階を並べて可視化: ROI / 1D プロファイル / 分類結果 / 最終値と確信度
- ここだけ DOM 依存。テストは E2E 不要（Phase 0 では目視確認ツールと割り切る）

### Step 0-7: 実画像フィクスチャで調整

**着手済み。現在の正解率 26% で、出口条件 90% には未達。**

実装したもの:

- `core/locate.ts` — 背景推定 → 最大連結成分 → PCA で主軸検出。
  長軸方向の太さ分布からリード線を除いた本体範囲を求める
- `core/rectify.ts` — 回転バウンディングボックスに沿った切り出しと水平化
  （双一次補間。OpenCV.js を入れずに済ませた）
- `core/bands/extent.ts` — プロファイル内で本体が占める範囲の特定
- `tests/fixtures/` — sample/ 全件を通す回帰テストと閾値掃引

計測結果（sample/ 39 枚）:

| 段階 | 結果 |
| ------ | ------ |
| 抵抗器の位置・角度検出 | **39/39 成功** |
| バンドのデコード成功 | 25/39 |
| 値の一致 | **10/39 (26%)** ※閾値 bodyΔE=4, minWidth=4 |

#### 判明した問題

1. **ROI 端の背景が偽バンドになる** → `bodyExtent` の導入で解決済み（0% → 15%）
2. **本体色と黄バンドが分離できない**（未解決）。CIEDE2000 は高彩度域の色差を
   圧縮するため、本体ベージュ（b\*24）と黄バンド（b\*55）の ΔE が閾値を下回り、
   黄バンドが本体として除去される
3. **基準色が実写とずれている**（未解決）。特に紫が灰に、銀が赤に誤分類される
4. **基準色の自動較正が失敗**（未解決）。正解値からバンド列を逆算して
   ランと突き合わせる方式を試したが、そもそもラン抽出が不安定なため
   割り当てが破綻する（「黒」が L\*63 の茶系として集計された）

#### セグメンテーションの順序反転（実施済み）

問題 2〜4 の根本は、**画素ごとに分類してからランに束ねる順序**にあると
判断し、順序を反転した（`core/bands/runs.ts`）。

1. 先に**隣接サンプル間の ΔE** で切れ目を見つけてランに分割する（分類しない）
2. ラン単位で集約した Lab を 1 回だけ分類する
3. 本体は「最も面積の大きいラン群」として決める（絶対閾値をやめた）

得られたもの:

- **本体色テーブルへの依存が消えた**。緑や青のボディでも同じ仕組みで扱える
  （ソ連製の緑ボディを想定したテストを追加）
- **バンドの分離精度が上がった**。例えば `08-47ohm` は以前は 2 本しか
  取れなかったが、正しく 4 本に分かれるようになった
- 失敗の質が「バンド本数が合わない」から「色の分類が違う」に移った。
  後者のほうが較正で対処しやすい

**ただし end-to-end の正解率は 26% → 18% に下がった。**
以前の 26% は 39 枚に対して閾値を調整した結果で、本数が合わないまま
偶然値が一致していたケースを含む。順序反転は構造としては正しいが、
数字の上では改善していないことを記録しておく。

#### 残る課題

較正がまだブートストラップできない。正解値から逆算したバンド列と
ラン数が一致する画像が 39 枚中 4 枚しかなく、基準色を集計するには
サンプルが足りない（紫・白・灰・青は 0 件）。

ラン数が合わない主因（推定）:

- 円筒形ボディの**陰影勾配**。長軸方向に明度が変化するため、切れ目が
  余計に入る。色順応補正は全体の一様なずれしか直せない
- **鏡面反射**のハイライトが独立したランになる
- バンド端の**ぼけ**が中間色の細いランを作る

#### 明度の局所正規化（試したが効果なし）

陰影勾配がランの過分割を招いていると考え、幅の広い移動中央値を
ベースラインとして明度から引く処理を実装した（`core/bands/normalize.ts`）。

**結果: 正解率 18% → 15%。改善せず。** 差は 1 枚ぶんで誤差の範囲だが、
効果を確認できていないものを既定で有効にはしないため
`normalizeShading` は既定 false。モジュールとテストは残してある
（基準色を較正したあとに再評価する価値はある）。

#### 現時点の総括

| 手を入れた箇所 | 正解率 |
| ---------------- | -------- |
| 初回計測 | 0% |
| 本体範囲の特定（`bodyExtent`） | 15% |
| 閾値の掃引 | 26% |
| セグメント順序の反転 | 18% |
| 明度の局所正規化 | 15% |

閾値の掃引で得た 26% は 39 枚に合わせ込んだ数字で、汎化性能ではない。
**パラメータ調整では出口条件 90% に届かない**というのが現時点の結論。

律速は基準色テーブルであり、その較正には安定したラン抽出が要る、という
相互依存を崩せていない。次に検討すべき選択肢:

1. **正解ラベルを手で与える**。数枚について「このランがこの色」と人手で
   対応付ければ、較正のブートストラップが成立する。少数でよい
2. **色の絶対値をやめる**。バンド同士の相対関係（どれが最も暗いか、
   どれが最も彩度が高いか）で分類する。照明条件への依存が減る
3. **Phase 0 の前提を見直す**。設計メモは「白背景・水平配置」を前提に
   しているが、sample/ の写真は背景も照明もばらばらで、この前提から
   外れている。前提に合う写真を撮り直せば、Phase 0 の完了判定としては
   正しい評価になる

#### 学習ループの導入（選択肢 1 を実施）

「推測 → 人手で修正 → 較正」のループを組んだ。

実装:

- `core/color/palette.ts` — 基準色を値として持ち回せるようにした。
  `classifyBandColor` / `segmentBands` / `analyzeRoi` が引数で受け取る
- `core/bands/align.ts` — 抽出したランを既知のバンド列に**動的計画法で
  対応付ける**。余分なラン（反射・ぼけ・背景の残り）を飛ばせるので、
  本数一致を要求しなくてよい
- `tests/fixtures/calibrate.test.ts` — 対応付け結果から色ごとの Lab を
  集計し `sample/palette.json` に書き出す。`sample/labels.json` に
  人手の正解を置けばそちらが優先される
- デバッグページ — 推測したバンド色をプルダウンで直すと、`labels.json`
  に貼れる形の JSON が出る

効果:

| 指標 | 前 | 後 |
| ------ | ---- | ---- |
| 較正に使える画像 | 4/39 | **19/39** |
| 正解率 | 8% | **23%** |

DP アライメントの導入が効いた。較正は 1 回で収束する（反復しても変化なし）。

#### GUI を解析経路と揃えた

デバッグページがテストのフィクスチャハーネスと違う経路を使っていたので揃えた。

- 抵抗器の**自動検出と水平化**（`locate` + `rectify`）を GUI でも使う。
  検出した回転ボックスは元画像に重ねて表示する。手動ドラッグも残してある
- **学習パレットを読み込む**。dev サーバーに `/palette.json` を配信する
  プラグインを足し、隣の作業用リポジトリの学習結果を参照する
  （ビルド成果物には含めない）
- **ラベルをためて一括で出せる**ようにした。localStorage に保存するので
  リロードしても消えない

#### 効果が無かった変更（記録）

| 試したこと | 結果 |
| ------------ | ------ |
| 太さ推定を最大値から 90% 分位点へ | 23% → 15%。外れ値に強いはずだが悪化 |
| ROI を長軸解像度で指定（240px 幅） | 23% → 13%。バンドの解像度は律速ではなかった |

いずれも計測に従って元に戻した。`rectify` の `targetWidth` は選択肢として
残してある（既定では使わない）。太さ推定の分位点は定数 1（＝最大値）。

**教訓**: 39 枚では 2〜3 枚の差が 5〜8 ポイントに相当し、判断の根拠として
弱い。写真を増やさないと、この種の調整は改善か偶然かを区別できない。

依然として 90% には遠い。学習した Lab を見ると、既定値との差が大きい
（例: 紫は a\*39 b\*−41 と推定していたが、実写では a\*10 b\*−1 とほぼ無彩色）。
残る精度不足は、人手ラベルを増やして学習サンプルを厚くするか、
選択肢 3（前提に合う写真の撮り直し）で対処する。

- 手持ちの抵抗器を白背景・水平で 20 枚程度撮影、正解 JSON を付けて
  `tests/fixtures/` に格納（1枚数百KBに圧縮）
- フィクスチャ一括実行テストで成功率を計測 → 閾値・基準色を調整
  - 較正対象: `color/colors.ts` の基準 sRGB 値、`classify.ts` の
    `MAX_ACCEPTABLE_DELTA_E` / `DEFAULT_BODY_DELTA_E`、`segment.ts` の
    `DEFAULT_MIN_BAND_WIDTH`、`profile.ts` の `DEFAULT_CENTER_FRACTION`
- 撮影時は青ボディの金属皮膜（白/銀バンドの低コントラスト）を必ず含める
- **ここで精度が出ない場合、Phase 1 に進まない**（設計メモの鉄則）

## 3. Phase 1 — リアルタイム化(単一抵抗器)

- `getUserMedia` + `requestVideoFrameCallback` + `createImageBitmap` transfer
- Worker 骨格(検出なし・中央固定 ROI で色帯解析のみ)
- OffscreenCanvas 2D による回転切り出しユーティリティ(Phase 3 の OBB に備え先行実装)
- 座標変換モジュール(video 内在解像度 ↔ CSS 表示座標)を一箇所に
- `<video>` + `<canvas>` オーバーレイ、UI ガイド枠(白基準を兼ねる)
- WB ロック(Chromium のみ)の feature detection と適用
- UI フレームワーク採否をここで決定

## 4. Phase 2 — 複数対応・トラッキング・時間方向投票

- 中心点距離マッチングの簡易トラッカー + ID 管理
- ID ごとに直近 10〜20 フレームの多数決、確信度未満は「?」表示
- ラベルの DOM 要素化（`transform: translate()`）

## 5. Phase 3 — YOLO26-OBB 導入

- データ: 300〜500 枚撮影 → Roboflow/Label Studio でアノテーション
  （照明色温度・WB・露出・回転・ぼけの augmentation を強めに）
