# OhmLens — 色判定方式の検討

2026-07-27 作成。色分類まわりで「別方式に置き換える／複数方式を併用する」案を
検討した記録。**結論としてボトムアップ分類はそのまま残し、値の確定を
トップダウン候補照合に作り直す案（§5）だけを有力候補とする。**

前提は [01-設計.md](01-設計.md) §2 [2]/[3]・[4]、および実装済みの
`core/bands/classify.ts` / `core/value/eseries.ts`。

## 1. 現状の色判断

Lab + ΔE2000 の最近傍分類がすでに実装済み。処理は次の順。

1. 基準色テーブルを sRGB で定義（バンド 12 色 + 本体色 2 色、`core/color/colors.ts`）
2. 起動時に Lab へ変換し、色差計算用に前処理してモジュール定数に固定
3. whiteBalance の色順応補正済み Lab と全基準色の ΔE2000 を取り、最小のものに分類
4. 確信度 = 最近傍への絶対的な近さ（ΔE 40 を上限）× 次点候補とのマージン

確信度が閾値未満なら値を出さず「?」を表示する方針（設計メモ §2 [5]）と接続する。

## 2. 色の「近さ」を測る一般的な方法

| 手法 | 概要 | 知覚との一致 |
| ------ | ------ | ------ |
| RGB ユークリッド距離 | RGB を 3 次元ベクトルとみなし距離を取る | 低い |
| 重み付き RGB（redmean） | R の大きさに応じて重みを変える近似式 | やや改善 |
| HSV / HSL の色相比較 | 色相環上の角度差で判断 | 暗い色・低彩度色で破綻 |
| Lab + ΔE76 | Lab 空間でのユークリッド距離 | 良い |
| Lab + ΔE2000 | 明度・彩度・色相ごとに知覚特性で補正した色差式 | 業界標準（採用中） |
| OKLab | 近年の知覚均等色空間。ユークリッド距離でもかなり良い | 良い |

要点は**知覚的均等性**。人間の目は色によって感度が違う（緑の変化に敏感、青に鈍い）
ため、「数値上の距離が等しい ＝ 見た目の差が等しい」となる空間で測る必要がある。
Lab はそのための空間で、ΔE2000 は Lab に残る歪み（特に青領域と低彩度域）を
補正した色差式。

## 3. 検討: RGB をベクトルとみなし頂点間距離で判定する

**不採用。** シンプルで高速だが、この用途には向かない。

- **知覚的に不均等**: 茶 `(102,51,12)` と赤 `(200,30,30)` のような微妙なケースで、
  距離の大小が人間の判断と一致しない
- **明るさと色味が絡み合う**: 照明が暗くなると RGB 全チャンネルが一様に下がり、
  ベクトルが原点方向へ移動する。「暗い赤」が茶より黒に近くなる類の誤分類が起きる。
  Lab は明度 L と色味 a/b が分離されているのでこの影響を切り分けられる
- **照明の色被りに弱い**: Web カメラの WB が揺れると RGB 値は全体にシフトする。
  本体色アンカーによる相対分類（設計メモ §2）は Lab 上での補正が前提で、
  RGB 距離では素直に実現できない

なお「基準色ベクトルの最近傍を探す」という発想自体は現行実装と同一であり、
違いは**距離を測る空間と距離関数だけ**。ΔE2000 の計算コストが問題になった場合の
軽量代替は、RGB 距離ではなく **OKLab + ユークリッド距離**を検討する。

## 4. 検討: 複数の距離指標で多数決を取る

**不採用。** ΔE2000 / OKLab / HSV などを並列に走らせて投票させる案。

多数決が効くのは各判定器の**誤りが独立している**とき。しかし色距離の指標はどれも
同じ 1 画素の RGB 値から決まる決定的関数で、誤りの原因（照明の色被り、グレア、影、
カメラの色再現）が共通する。画素値そのものがズレたら全指標が同じ方向に間違える。

- 指標が一致するケース → もともと 1 指標でも当たる
- 指標が割れるケース → どれを信じるかの重み・閾値調整が必要で、結局較正データが要る

得られるのは「割れたら確信度を下げる」効果だが、それは現行の次点マージンが
すでに担っている。一方で閾値チューニングと較正の手間は指標の数だけ増える。

### 効くのは「誤差源が独立した証拠」を重ねること

同じ画素を別のものさしで測るのではなく、**別の情報源**を段違いに重ねる。

| 層 | 内容 | 状態 |
| ------ | ------ | ------ |
| ① 空間方向の集約 | バンド内の複数画素の中央値 Lab を取ってから分類（`bands/runs.ts`） | 実装済み |
| ② 意味的整合性 | E24/E96 スナップで実在しない値を棄却（`value/eseries.ts`） | 実装済み（→ §5 で格上げ） |
| ③ 混同ペア専用の二次判別 | 上位 2 候補が既知の混同ペアのときだけ、分離に効く軸で再判定 | 未実装・§5 で代替可能 |
| ④ 時間方向の多数決 | 複数フレームの読み値を投票（設計メモ §2 [5]） | Phase 1 |

③ の具体案は、茶/赤 → 明度 L と彩度 C、金/黄 → 明度 L、灰/銀/白 → 明度 L のみ、
というようにペアごとに 1 軸で再判定するもの。`rankBandColors()` が上位候補を返す
設計はこの拡張の受け口だが、**§5 を採用すれば系列制約が同じ仕事を自動でこなす**
ため、個別ルールとして作り込む必要は薄い。

## 5. 検討: E24/E96 の候補値から色列を逆生成して照合する（有力）

**有力。導入判断はフィクスチャでの比較後。**

現行の「観測 → 色を確定 → 値に変換 → 事後スナップ」というボトムアップを、
「**ありうる値の候補 → 期待される色列 → 観測との一致度で採点**」というトップダウンに
反転させる案。OCR の辞書（レキシコン）照合と同じ構図。

### 効く理由

現行構成では、第 1 バンドが茶/赤で拮抗していても分類段階でどちらかに決め打ちして
しまい、その誤りを後段のスナップでは救えないことがある。候補照合なら判断を最後まで
保留できる。観測が「茶?赤? - 黒 - 赤 - 金」の場合:

- 候補「赤黒赤金 = 2.0kΩ」→ E24 に存在、第 1 バンドの ΔE がやや大きい
- 候補「茶黒赤金 = 1.0kΩ」→ E24 に存在、全バンドの ΔE 合計が最小 → 採用

曖昧な 1 バンドを、**残りのバンドの明瞭さ**と**実在する値かどうかという独立した
事前知識**で補完できる。§4 ③ の混同ペア個別ルールより一般的な解になる。

### 計算量

候補空間は小さい。4 バンド E24 なら 24 仮数 × 乗数 ~10 × 許容差色 × 読み方向 2 で
数百通り、5 バンド E96 でも数千通り。各バンドの「12 基準色それぞれへの ΔE」を先に
1 回だけ計算して行列（バンド数 × 12）に持てば、候補 1 件の採点はテーブル引きの
足し算だけになる。リアルタイムでも問題にならない。

### 必須の設計上の注意

#### (1) 事前知識が値を「捏造」しないようゲートする

この方式の本質的リスクは、検出ミスや規格外品（ゼロオーム抵抗、損傷品）に対しても
*何かしらの*「最もマシな実在値」を返してしまうこと。「誤った値を自信ありげに
出さない」原則（CLAUDE.md）に直結するので、次の 2 条件で必ずゲートする。

- 最良候補でも、いずれかのバンドの ΔE が閾値超え → 「?」
- 最良候補と、**別の抵抗値を指す**次点候補とのスコア差が小さい → 「?」

特に後者の「値レベルのマージン」は現行の「色レベルのマージン」より意味のある
確信度になる。ユーザが知りたいのは「色を当てられたか」ではなく
「値を間違えていないか」であるため。

#### (2) 既存の段とは置換ではなく統合

- `value/direction.ts` の「ambiguous なら呼び出し側で E 系列適合により決める」
  という保留は、両方向を候補として採点すればそのまま解消される
- `value/codeTable.ts` の digitOf / multiplierOf を逆引きすれば
  「値 → 期待色列」の生成は容易
- 事後スナップ（`value/eseries.ts`）は候補生成そのものに吸収される。ただし
  系列の選び方（許容差バンドで E24 / E96 を先に決める、設計メモ §2 [4]）は
  候補生成の制約としてそのまま引き継ぐ
- 個別バンド分類 `classifyBandColor()` は捨てず、デバッグ表示とゲート判定用に残す

## 6. 判断の進め方

`sample/` の実画像フィクスチャで現行方式と候補照合方式を並べ、次を比較してから
導入を決める。

- 正答率と「?」率
- **現行が自信を持って誤読するケース**が減るか
- 逆に**規格外品を実在値に引き寄せて誤読するケース**が増えないか

§4 ③ の混同ペア専用判別は、まず誤分類がどのペアに集中しているかを測ってから
判断する（茶/赤に集中していなければ導入不要）。
