# OhmLens — バンド境界の検出指標

微分の絶対値の和

```text
abs = L1·|dL/dx| + A1·|da/dx| + B1·|db/dx|
```

でバンド境界を拾うとき、係数 `L1 / A1 / B1` に何を置くべきかを実測から決める。
[12](12-HiRes論文の施策を試した結果.md) の続き。

> **結論: 固定係数を置くなら 1 : 2.8 : 1.9。ただし推奨は係数を置かず、
> 1 枚ごとに各チャンネルの MAD で正規化すること（§2）。
> それより先に、微分の前に平滑化を入れるほうが効く（§4）。**

## 1. 測定 — L\* は「信号が大きい」のではなく「雑音も大きい」

`sample/` の 48 枚で、中心線プロファイルの中心差分をチャンネルごとに測った。
雑音床は MAD（中央絶対偏差）、信号はバンド境界の立ち上がりを代表する
`|d|` の 95 パーセンタイルを使う。MAD は外れ値に引っ張られないので、
境界を含んだ系列からでも雑音床だけを取り出せる。

```bash
npx tsx scripts/dbgGrad.ts
```

| 系列 | MAD（雑音床） | p95（境界の大きさ） | SNR = p95/MAD |
| ------ | ------ | ------ | ------ |
| dL\*/dx | 1.47 | 16.07 | 9.8 |
| da\*/dx | 0.52 | 7.34 | 10.7 |
| db\*/dx | 0.77 | 7.08 | 8.3 |

いずれも 48 枚の中央値。読み取れることは 2 つ。

- **生の振幅では L\* が a\*・b\* の 2 倍以上ある。** 係数をすべて 1 にした素の和は、
  実質「L\* に重み 2」を置いているのと同じ
- **しかし L\* は雑音も 2〜3 倍大きい。** SNR で見ると 3 チャンネルはほぼ横並び
  （9.8 / 10.7 / 8.3）

L\* が大きく見えるのは信号が強いからではなく、信号も雑音も一緒にスケールが
大きいだけ。境界検出で効かせたいのは SNR なので、**雑音で割るのが筋**になる。

## 2. 係数の答え

固定値を置くなら、`1/MAD` の比がそのまま答えになる。

```text
L1 : A1 : B1 = 1 : 2.8 : 1.9
```

ただし**固定値は勧めない**。`MAD(dL)` は 48 枚で 0.21〜7.30 と 35 倍ばらつく。
露出・ボディの質感・ROI の解像度で桁が動くので、全枚数の中央値から決めた
固定係数はどの 1 枚にも最適にならない。代わりに 1 枚ごとに正規化する。

```text
abs = |dL/dx|/σL + |da/dx|/σa + |db/dx|/σb      σ は各画像・各チャンネルの MAD
```

これなら係数は「そのショットの雑音量」に自動で合う。ゼロ割は下限（0.05 程度）で
止める。

## 3. 和より max

```text
score = max(|dL|/σL, |da|/σa, |db|/σb)
```

境界は「どれか 1 チャンネルに出れば境界」である。黒・灰・白・銀の境目は L\* にしか
出ず、茶・赤の境目は a\*・b\* にしか出ない。和にすると、片側に立った強い山が
他 2 チャンネルの雑音 2 本ぶんで薄まる。銀・灰・白が弱点である以上
（[12](12-HiRes論文の施策を試した結果.md) §9）、L\* 単独の境界を潰さない max のほうが噛み合う。

## 4. 係数より先に平滑化

現行の `differentiate` は素の中心差分で、雑音をそのまま増幅している。
**Savitzky–Golay（窓 5〜7、2 次）か Gaussian の 1 次微分（σ ≈ 最小バンド幅の 1/3）
に置き換えるほうが、係数を触るより大きく効く。** 係数は SNR を 1〜2 割動かす話だが、
平滑化は雑音床そのものを下げる。

## 5. まったく別の式

| 案 | 評価 |
| ---- | ---- |
| **マッチトフィルタ** | バンド幅は本体長の 5〜8% と既知なので、その幅の矩形と相関を取る。境界を単独で探さず「立ち上がり + 立ち下がり」の対で探すので、単発ノイズに原理的に強い。**微分系より筋が良い** |
| **変化点検出（CUSUM 系）** | 現行 `splitRuns` の発展形。区間平均を使うので雑音が 1/√N に落ちる。局所微分の弱点をそもそも持たない |
| Mahalanobis 距離 | 正規化 max の一般形。露出揺れは 3 チャンネルに相関して乗るので理屈は正しいが、共分散の推定に標本が要る |
| ΔE2000 の局所差 | 分類側と指標が揃う利点はあるが、**低彩度域で差を圧縮する**ので銀・灰・白の弱点が悪化する。この案件では非推奨 |
| HyAB 型（`\|dL\| + √(da² + db²)`） | [09](09-色空間と色差指標の検討.md) §5.3 で分類用として実測否定済み（10/15 → 9/15）。境界検出は別タスクだが、同じ轍に見える |

## 6. 現行の分割は微分ではない

[`core/bands/runs.ts`](../src/core/bands/runs.ts) の `splitRuns` は、
各サンプルと**伸長中のランの平均色**との ΔE76 が 20 を超えたら切る領域成長型で、
局所微分は使っていない。そして `ΔE76 = √(dL² + da² + db²)` は
**係数をすべて 1 にした L2 版そのもの**である。

abs を新しい指標として入れるなら、この既存指標と何が違うのかを決めてから入れる。
でないと同じことを 2 か所で管理することになる。

## 7. 境界の正解データ — 単位は % でよい

係数の良し悪しを測るには境界の正解が要る。`labels.json` はバンドの**色列**であって
位置ではないので、別に作る必要がある。0 から手入力するのは現実的でないので、
**推定値を出力して手で直す**形にする。

### 単位

**% でよい。** 焼き込み画像の X 軸が既に「検出した赤い四角形の長さを 100%、
左端を 0%」の % 目盛りなので、**目で読んだ値をそのまま書き直せる**のが決め手。
編集のループが短いことが、この種のデータでは精度より効く。

ただし条件が 1 つある。

> **% の基準である検出ボックスも一緒に記録すること。**

% の基準（赤い四角形）は検出器の推定結果なので、`locate` や `refineBoxExtent` を
直すと同じ物理的な境界が別の % に移る。ボックス（`centerX` / `centerY` /
`angleDeg` / `length` / `thickness`）を併記しておけば % と元画像座標が可逆になり、
検出器を直したときに正解データを再投影できる。記録しないと、正解が黙って腐る。

### 精度

ROI の列数は 48 枚で中央値 115、最小 86、最大 250。X 軸が映す範囲は
ROI 余白 0.28 込みで -28%〜128% の 156% ぶんなので、1 サンプルは

| ROI 列数 | 1 サンプルあたり |
| ------ | ------ |
| 86（最小） | 1.81% |
| 115（中央値） | 1.36% |
| 250（最大） | 0.62% |

**整数 % で足りる**（0.5〜1.8 サンプル相当）。0.1% 刻みは元データの分解能を超える。

### 形式

境界点の羅列ではなく、**バンドの区間 `[開始%, 終了%]` を色列と対にする**のがよい。

- `labels.json` の色列と 1 対 1 で対応するので、本数の食い違いがその場で分かる
- 境界は区間の端として導けるが、逆は導けない
- 区間の隙間が本体なので、本体範囲の正解も同時に得られる

あわせて、**人手で確認済みかどうかの旗**を 1 枚ごとに持たせる。種として吐いた
推定値と、人が直した値が混ざると、何を信じてよいか分からなくなる。

```json
{
  "46-82kohm-5pct-carbonfilm-grey.jpg": {
    "verified": false,
    "box": { "centerX": 400.2, "centerY": 233.1, "angleDeg": -1.2, "length": 110.4, "thickness": 30.1 },
    "bands": [
      { "color": "grey", "start": 12, "end": 20 },
      { "color": "red", "start": 46, "end": 54 },
      { "color": "orange", "start": 63, "end": 71 }
    ]
  }
}
```

### 実装

| 道具 | 役割 |
| ------ | ------ |
| [`core/bands/boundaries.ts`](../src/core/bands/boundaries.ts) | 型・% 変換・種の合流・採点 |
| `npx tsx scripts/seedBoundaries.ts --write` | 現行の検出から種を作る。**`verified: true` は上書きしない** |
| `npx tsx scripts/scoreBoundaries.ts` | `verified` のものだけで採点する。バンド単位の一致・境界点の再現率と適合率・**段階別の生存**（§11） |
| `./doDetect.sh` | `verified` の区間を Lab グラフに緑の帯で重ねる |

種は現行のランからただで作れる（`result.runs` の `start` / `end` を
`alongPercentAt` で % に写すだけ）。採点時の一致判定は **±2%（≈1.5 サンプル）**
を既定にした（`--tol` で変えられる）。

手で直す手順は次のとおり。

1. `./doDetect.sh 46` で焼き込み画像を作る
2. Lab グラフの X 軸（%）を見ながら `sample/boundaries.json` の数字を直す
3. 直したエントリを `"verified": true` にする
4. `./doDetect.sh 46` をもう一度走らせると、直した区間が緑で重なる
5. `npx tsx scripts/scoreBoundaries.ts` で成績を見る

## 8. 注意 — 効果が出ない可能性を先に見積もる

[09](09-色空間と色差指標の検討.md) の掃引では、`edgeΔE` を 7 / 9 / 12 と振っても
**正解 28 のまま動かなかった**（分割パラメータは既に平坦域）。境界検出はもう
律速ではない可能性が高い。係数を詰めても正解数が動かなかったときに
「効かなかった」と判断できるよう、**境界位置そのものの一致率**で測ること。
最終的な正解数だけで測ると、パレットやデコード側の要因に埋もれて判断できない。

## 9. 進める順序

1. 微分の前に平滑化（§4）— **実施済み**（§10）
2. MAD 正規化 + max（§2・§3）— **実施済み**（§10）
3. 境界の正解データを数枚ぶん作って、①②を境界一致率で測る（§7）— **1 枚で実施**（§10）
4. 正解を 10 枚まで増やしてから、`trimEdgeRuns` と `recover` の噛み合わせを試す（§10）
5. 正解 21 枚で段階別に測り直す（§11）— **実施済み。分割が主犯と判明したが、
   直しても値は良くならない。次に効くのは分類・パレット側**

## 10. 実測 — 指標を良くしても拾えないものは拾えない

§2〜§4 を [`core/bands/edgeStrength.ts`](../src/core/bands/edgeStrength.ts) に実装し
（Savitzky–Golay の 1 次微分 → チャンネルごとに MAD で正規化 → max）、
人手で境界を確定した `46-82kohm-5pct-carbonfilm-grey.jpg` で測った。

```bash
npx tsx scripts/dbgEdgeStrength.ts
```

| 指標 | 境界とそれ以外の比 | 上位一致 |
| ------ | ------ | ------ |
| 素の abs（中心差分の和） | 1.95 倍 | 5/8 |
| 平滑化 + 正規化 max | **3.28 倍** | 5/8 |

**コントラストは 1.7 倍に改善したが、拾える境界の本数は変わらない。**
理由は境界ごとに見ると分かる。

| バンド | 本体との ΔE76 | 指標の強さ（雑音比） | 山の順位 |
| ------ | ------ | ------ | ------ |
| 金 26〜32% | **2.2** | 1.2〜1.4 | 15 位・21 位 |
| 橙 47〜53% | 36.4 | 8.3 | 3 位・4 位 |
| 赤 65〜71% | 45.7 | 12.8 | 1 位・2 位 |
| 灰 82〜88% | **13.8** | 4.2（左端のみ。右端は山なし） | 7 位 |

- **金は情報が無い。** 本体との色差が 2.2 で、雑音床の 1.2〜1.4 倍にしかならない。
  指標をどう変えても、しきい値をどこに置いても復元できない
- **灰は情報がある。** 色差 13.8・雑音の 4.2 倍。分割のしきい値 20 に届かないだけ
- ただし灰の 4.2 倍は、**肩の照り返し（7%・12% で 3.4〜4.6 倍）と同じ高さ**。
  全体のしきい値を下げると肩も一緒に入る

### 誤読に至る連鎖

1. 金が見えない（ΔE 2.2）
2. 灰がしきい値に届かない（ΔE 13.8 < 20）
3. 残るランが橙・赤の 2 本になり、`MIN_BANDS`（3）を割る
4. **3 本に届かないため、捨てるはずの肩のランが残る**
   （[`segment.ts`](../src/core/bands/segment.ts) の `trimEdgeRuns` は
   `MIN_BANDS` を割ってまで端を落とさない）
5. 肩 + 橙 + 赤で復号され、まったく違う値が出る

**直すべきは指標ではなく 2 と 4。** しかも「位置を絞って弱い基準で拾い直す」
仕組みは既にある（[`recover.ts`](../src/core/bands/recover.ts) の
`RECOVER_DELTA_E = 9`）。灰の 13.8 はこの基準なら通る。効いていないのは、
拾い直しの起点になる「3 本目」が肩のランになっているため。

### バンドの幾何は当てにしすぎない

拾い直しは位置の予測に頼るので、間隔がどれだけそろっているかを 28 枚
（正解かつ 3 ラン以上、計 109 本）で測った。

| 量 | 中央値 | 10% 点 | 90% 点 |
| ------ | ------ | ------ | ------ |
| バンド幅 [%] | 8.2 | 4.1 | 10.9 |
| 芯間隔 [%] | 19.2 | 12.5 | 24.1 |
| 間隔の変動係数 | 0.148 | — | 0.220 |

変動係数が 0.15 未満なのは 28 枚中 15 枚。**固定刻みの櫛やマッチトフィルタは
根拠が弱い**（§5 の評価を下方修正する）。予測位置に幅を持たせて弱い基準で
検査する、今の `recover.ts` の作法のほうが実測に合っている。

### 「端のランを常に落とす」は実測で否定した

上の連鎖の 4 を直す案 — 肩のランを「本数合わせのために残す」のをやめて
2 本のまま `recoverFromPair` に渡す — を実装して 48 枚で測った。

| 設定 | 正解 | 誤答 | 保留 |
| ------ | ------ | ------ | ------ |
| 現行（3 本を割るなら端を残す） | **32** | **0** | 16 |
| 端に接するランは常に落とす | 31 | 1 | 16 |

| 検体 | 変化 |
| ------ | ------ |
| `17-680ohm` | ○ → **×**（680Ω → 4.7GΩ）。端に接していた**本物のバンド**が落ちた |
| `46-82kohm` | △ → △（ラン 3 → **4**）。灰は拾い直せたが、値はまだ出ない |
| `51-39kohm` | △ → △（ラン 1 → 0） |

**`MIN_BANDS` を守る現行の規則は正しい。** `trimEdgeRuns` のコメントにある
「端に接していても本物のバンドであることはある」は `17-680ohm` で実証された。
1 枚（46）を部分的に改善する代わりに、正解していた 1 枚を壊す。**採用しない。**

収穫は 46 でランが 3 → 4 に増えたこと。**灰は拾い直しの経路に乗せれば取れる**
（`RECOVER_DELTA_E = 9` は ΔE 13.8 の灰を通す）ことが確かめられた。
必要なのは「端を落とす」ことではなく、**肩のランと本物のバンドを見分ける手段**。

### 結論

- `edgeStrength` は**確信度や診断の材料としては有用**（コントラスト 1.7 倍）。
  ただし分割の本数を増やす力は無いので、`splitRuns` の置き換えには使わない
- 端の切り落としを緩める案は否定済み。**繰り返さないこと**
- 残る筋は「肩のランを色や幅で見分ける」方向。ただし**正解が 1 枚では設計できない**。
  → 正解 21 枚で測り直した結果、この筋は**下方修正**した（§11）。余分なランは
  8 本しかなく、失われる 15 本のほうが桁違いに多い。
  `boundaries.json` の `verified` を 10 枚まで増やしてから取りかかる

## 11. 実測 — 人手の境界を較正の教師にしても、パレットは良くならなかった

§7 の `boundaries.json` を較正の教師として使う案を実装して測った。
`verified` のある検体では、DP による対応付け（`align.ts`）を飛ばして
区間の色を直接取る。**対応付けの推測が要らなくなるので、教師としては
明らかに正確になる。**

実際、金の学習値は経路によってこれだけ違った。

| 経路 | 金の実測 Lab | 件数 |
| ------ | ------ | ------ |
| 人手の境界だけ | **L81 a5 b28** | 15 |
| 推測混じり（従来） | L99 a3 b10（ほぼ白） | 35 |

[09](09-色空間と色差指標の検討.md) §1 が記録した「金がほぼ白として学習される」
現象が、**推測経路だけで起きている**ことが裏付けられた。

### それでも成績は上がらない

`verified` 13 枚（01〜14 と 46）で 5 通り試した。基準は 正解 32 / 誤答 0。

| 変種 | 正解 | 誤答 | 値一致 |
| ------ | ------ | ------ | ------ |
| 基準（従来どおり） | **32** | **0** | 34/48 |
| A. 人手の色を標本に加える | 32 | 0 | 33/48 |
| B. 人手が 3 件以上ある色は人手だけ | 27 | 4 | 30/48 |
| C. B + 品質の関門（ずれ 25 超は棄却） | 30 | 2 | 31/48 |
| D. A + 品質の関門 | 30 | 2 | 32/48 |
| E. D で棄却分を推測経路に落とす | 26 | 3 | 28/48 |

**どれも基準を超えない。** 正確な教師を足すほど成績が落ちる、という逆説が起きる。

理由は、パレットが「実物の色の記述」ではなく
**最近傍分類が当たるように調整された錨**だから。推測経路は対応付けに失敗した
写真を `MAX_ALIGN_COST` で捨てており、その取捨選択ごと現在の成績に織り込まれている。
そこへ、正しいが極端な標本（同じ金でも写真によって L81 から L135 まで散る）を
足すと、中央値が動いて分離が崩れる。

### 学んだこと

- **較正は反復である。** `calibrate` は前回の `palette.json` を起点に読み、
  結果を同じファイルに書く。実験でパレットを汚すと、コードを戻しても
  成績が戻らない。**変種を測る前に `git checkout sample/palette.json` をすること**
- 正解 13 枚では、34 枚ぶんの推測に統計で勝てない。人手の境界が
  **30 枚を超えたあたりで再測**する価値がある
- 金の L81 と L99 の差は本物なので、**枚数が増えれば効くはず**という見込みは残る

実装は差し戻した。`boundaries.json` の道具（種の生成・採点・焼き込みへの重ね描き）
はそのまま使える。

## 11. 実測 — 分割は直せる。ただし値は良くならない

正解が 21 枚（バンド 89 本）まで増えたので、§10 で「正解が 1 枚では設計できない」
と保留した検討をやり直した。

### 指標を「どの段で消えたか」に作り直した

境界点の一致（再現率 83%）だけでは打ち手が選べない。本体を丸ごと覆う 1 本の
巨大なランでも、端がたまたま正解の端に近ければ一致に数えてしまうためで、
**「ランとして切られていない」失敗が隠れる**。[`scoreBoundaries.ts`](../scripts/scoreBoundaries.ts)
に次の 2 つを足した。

- **バンド単位の一致**（区間の IoU）— 本数が合っているか
- **段階別の生存** — 正解のバンドが分割・本体除去・まとめ・端落とし・拾い直しの
  どこで消えたか。[`segment.ts`](../src/core/bands/segment.ts) の `bandRunStages`
  が途中経過を返す（`bandRuns` はこれを呼ぶ実装にしてあるので、診断が本番と
  違う道を通ることはない）

あわせて、正解を記録したときの箱と今の箱がずれていたら `[箱ずれ]` と印を付ける。
% は箱を基準にした相対位置なので、箱が動くと同じ境界が別の % に移る。

### 内訳 — 主犯は分割だった

| 段階 | 生き残った正解バンド |
| ------ | ------ |
| 分割 | 69 / 89 |
| 本体除去 | 68 / 89 |
| まとめ | 68 / 89 |
| 端落とし | 68 / 89 |
| 拾い直し（最終） | 74 / 89 |

失われた 15 本のうち **14 本が分割の段階で消えている**（内訳は金 13・銀 1・灰 1）。
本体除去は 1 本、端落としは 0 本。**`trimEdgeRuns` も本体クラスタも主犯ではない。**
§10 の「残る筋は肩のランを色や幅で見分ける方向」は下方修正する — 余分なランは
8 本しかなく、優先度は逆。

金と本体の ΔE76 は実測 4.1〜10.8 で、`EDGE_DELTA_E = 20` の半分以下。しかも
本体自身のばらつき（バンド外サンプルの 95 パーセンタイル）11〜21 と同等以下。
**一律のしきい値を下げる方向は原理的に無理**（下げれば陰影が先に切れる）。

### 試したこと 1 — 陰影の局所正規化: 効かない

金は「色相が本体と同じで L だけ凹む」ので、`normalizeLightness` で本体の L 勾配を
潰せば段差が浮くはず、と考えた。窓幅を振って分割で切れた本数を測った。

| 窓幅 | 正規化なし | 0.5 | 0.35 | 0.25 | 0.18 | 0.12 |
| ------ | ------ | ------ | ------ | ------ | ------ | ------ |
| 分割で切れた | 60 | 60 | 60 | 60 | 59 | 45 |

**1 本も増えない。** 勾配を消しても凹みの深さ（4〜11）は変わらず、しきい値 20 に
届かないままだから。`normalizeShading` は引き続き無効でよい。

### 試したこと 2 — 明度だけの切れ目: 分割は直るが値は悪化する

`splitRuns` に第二の基準を足した。「ランの平均から**明度だけ**が
`lightnessMargin` 以上離れたら切る」。ΔE では捕まらない金・銀がこれで切れる。

| マージン | 無効 | 12 | 8 | 7 | 6 | 5 | 4 | 3 |
| ------ | ------ | ------ | ------ | ------ | ------ | ------ | ------ | ------ |
| 分割で切れた | 63 | 66 | 66 | 71 | 75 | **76** | 76 | 74 |

**分割の段階は実際に直る**（63 → 76、余分なランは +4 だけ）。段階別に見ると
生存は 分割 60/77 → 80/85 に跳ね上がり、律速は本体除去へ移る。そこで
`isBodyLightnessExtremum` のマージン（従来 12 固定）も引数にして掃引した。

| 明度マージン | 極小マージン | 正解 | 誤答 | 保留 |
| ------ | ------ | ------ | ------ | ------ |
| **無効（現行）** | 12 | **32** | **1** | 15 |
| 6 | 12 | 32 | 2 | 14 |
| 4 | 12 | 31 | 1 | 16 |
| 5 | 12 | 31 | 4 | 13 |
| 8 | 8 | 29 | 5 | 14 |
| 5 | 6 | 29 | 3 | 16 |

（48 枚。`isReadableSize` の門を通さない分、`doDetect.sh` の数字とは 1 件ずれる）

**どの組み合わせも「正解が減る」か「誤答が増える」。** 金のランを見つけられても
その色を正しく当てられないので、保留だったものが誤答に変わるだけだった。
誤った値を自信ありげに出さない方針を正解数より優先するので**採用しない**。

`lightnessMargin` と `bodyExtremumMargin` は仕組みとして残し、
[`settings.ts`](../src/core/settings.ts) では無効（`Infinity` / 従来の 12）にしてある。
再測定したいときは掃引の入口として使える。

### §11 の結論

- **指標は「段階別の生存」で見ること。** 境界点の一致率は失敗を隠す
- 分割が主犯なのは確かめた。だが**分割を直しても値は良くならない**。
  §8 で見積もった「境界検出はもう律速ではない」が、正解 21 枚で裏づいた
- 次に効くのは分割ではなく**金の色を当てる側**（分類・パレット）。
  ランが取れていても色が当たらなければ、保留が誤答に変わるだけ
- 陰影の局所正規化・明度だけの切れ目は、いずれも**否定済み。繰り返さないこと**

## 12. 実測 — ラン数を直したのは分割ではなく「安全弁つきの拾い直し」だった

§11 の「分割は直せるが値は良くならない」を受けて、方針を変えた。
**ランを増やす操作と、値を守る仕組みを分離する。**

### 金属容疑の安全弁（デコード側）

金・銀の分類は原理的に立たない。学習パレットの金属色はアンカー依存の
二峰性で棄却済み（`docs/11` §8）で、既定の基準色も実写と 30〜44 ずれる。
そこで色で当てるのをやめ、**位置づけで縛る**ことにした。

[`jointDecode.ts`](../src/core/value/jointDecode.ts) に `bodyLab` を渡すと、
本体との CIE76 が 12 以下のラン（金属容疑）は:

- 色候補が金・銀に限られる（カラーコード表の制約で数字にならない）
- 捨てるコストが 0 になる（本数合わせで解釈が歪まない）

しきい値 12 は実測から: 金は本体と 4.1〜10.8、肩の照り返しは 10.6〜11.2、
本体に最も近い**数字**バンドは灰の 14.7。11 と 14.7 の間に置く。

これで「金属らしきランが増えても値は壊れない」が保証される。
安全弁単体では成績は不変（正解 32 / 誤答 0）。

### 拾い直しのしきい値を 9 → 3 に下げる

`recover.ts` の拾い直しは位置を予測してから探すので、全体の分割より弱い
基準を使ってよい — が、従来の ΔE 9 は金（本体との差 4〜11）の半分を
取りこぼしていた。下げる案は「誤答が増える」ため棄却されていた
（ΔE 5 で正解 26 — `docs/11` §3.5）。**それは安全弁が無かったから**である。

43 枚（正解バンド 155 本）で、安全弁の有無を分けて掃引した:

| recoverΔE | 安全弁 | バンド一致 | 余分 | 正解/誤答 |
| ------ | ------ | ------ | ------ | ------ |
| 9（旧） | あり | 130 | 11 | 32/1 |
| 4 | あり | 143 | 11 | 32/1 |
| **3** | **あり** | **145** | **9** | **32/1** |
| 2 | あり | 141 | 13 | 32/1 |
| 9 | なし | 130 | 11 | 32/1 |
| 5 | なし | 140 | 14 | **31/2** |
| 3 | なし | 145 | 9 | **30/2** |

（誤答 1 は `isReadableSize` の門を通さない測り方によるもので、門を通す
`doDetect.sh` では誤答 0）

- **安全弁ありでは、しきい値をどこまで下げても値が 1 つも動かない。**
  拾った弱いランは金属役割（値に影響しない許容差・確定済み倍率）に
  収まるか、タダで捨てられるかのどちらかしかないため
- **安全弁なしでは従来どおり誤答が増える**（30〜31 / 誤答 2）。
  旧しきい値 9 が正しかったのではなく、安全弁が無かっただけ
- 3 が頂点。2 以下は予測窓のなかの雑音を拾い始めて崩れる

### 分割マージンの再掃引（安全弁つき）— それでも駄目

§11 の `lightnessMargin` を安全弁つきで測り直し、あわせて本体吸収の
真因（凹み除外の絞り 0.85 が金の距離 4〜11 を弾けない）も直して掃引した。
結果はバンド一致 最大 +1 に対して正解 32 → 30〜31 か誤答増。絞りを 0 に
すると影のランが暴発する（余分 9 → 21〜29）。**分割経路は三度目の否定。**

### 結果

| 指標 | 施策前 | 施策後 |
| ------ | ------ | ------ |
| バンド一致（verified 39 枚・159 本） | 84% | **93%**（148/159） |
| 余分なラン | 10 | 10 |
| doDetect（43 枚） | 正解 32 / 誤答 0 | 正解 32 / 誤答 0 |

残る取りこぼし 11 本の内訳は 分割 9・本体除去 1・端落とし 1（金 8・銀 1 ほか）。
これらは拾い直しの発火条件（ラン 3 本・中央 40〜60%）の外にあるもので、
次に詰めるなら発火条件の拡張だが、収穫逓減に入っている。

### 教訓

- **「ランを増やす」と「値を守る」を同じ機構でやろうとしない。**
  分割のしきい値・基準色・拾い直しの強さはすべて両者のトレードオフに
  見えたが、安全弁を分離した途端にトレードオフが消えた
- 過去に棄却した施策でも、**棄却の理由が消えたら測り直す**。
  「ΔE 5 で正解 26」は施策自体の欠陥ではなく、守りの不在だった
